    第 1 章 开篇：为什么你的 RAG Demo 上不了线

    状态：v0.2 · 所属：第一部 知识入库 · 先修：会 Python、调过 LLM API

    1.1 失败先行：三个让 Demo 现场的提问

    先跑起来，再让它在三个问题上当场翻车。

    git clone https://github.com/Ming-H/tally.git && cd tally
pip install -r requirements.txt
python -m tally.cli ingest samples/    # 30 秒：摄取 3 家公司 5 份样例财报

    提问一：问一个库里没有的年份。

    python -m tally.cli ask "欧科亿 2030 年净利润预测"

    Tally 的回答：

    库里没有 2030 年期间的报告（现有期间：2026H1E、2026Q1…）。 对不上账，不硬答。

    一个「普通」RAG Demo 会怎么做？检索出 2026 年的数字，配上 「根据现有资料」的措辞，流畅地答非所问。Demo 缺的第一样东西： 知道自己不知道什么。

    提问二：问扣非净利润。 问「扣除非经常性损益后的净利润」， 典型 Demo 会答归母净利润的数字——词面 80% 重叠、向量相似度极高， 语义检索恰恰最喜欢这种「近而不同」。Demo 缺的第二样东西：口径。

    提问三：问趋势。 「最近几个季度利润走势」——让 LLM 自己逐期 检索，小模型会漏期、死循环、把「预计」答成「已实现」。 Demo 缺的第三样东西：把不可靠的环节交给可靠的代码。

    1.2 业界视角：RAG 的谱系与本书的位置

    背景速览

    RAG（Retrieval-Augmented Generation）由 Lewis et al. 2020 年提出 （arXiv:2005.11401）：生成前先 检索，用外部知识约束模型输出。此后业界把它走成了一条谱系 （Gao et al. 综述 arXiv:2312.10997）：

    代际 形态 典型特征
    Naive RAG 检索→拼接→生成 一把向量库，一把 prompt
    Advanced RAG 查询改写、重排、混合检索 上下文工程
    Modular/Agentic RAG 路由、纠错环、工具、规划 LLM 决定控制流
    可信 RAG（本书） 出口闸门、归因、拒答 答案凭什么出门

    前三代解决「检索得好不好」，第四代解决「答案可信不可信」—— 这正是 Anthropic 在 Building Effective Agents 里的提醒：从能工作的最简单结构开始，别上来就自主 Agent。 Tally 的答案是「自由规划、强制对账」：控制流可以交给模型， 出口必须留给代码。

    1.3 对账思想：Tally 这个名字

    中世纪的符木（tally stick）：债权双方把数目刻在木棍上，从中间 劈开，各执一半。对账时把两半合上——刻痕对得上，账才算数。

       你的那一半                原文的那一半
   ┌┐┬┐┬┐┬┐┬┐            ┌┐┬┐┬┐┬┐┬┐
   └┘┴┘┴┘┴┘┴┘  ←——对上——→  └┘┴┘┴┘┴┘┴┘
        答案里的数字句            证据池里的原文

    这个思想在学术界有个正式名字：归因（Attribution）。Rashkin et al. 的 AIS 框架（arXiv:2112.12870， ACL 版本）把标准定为 「一个知情读者会同意：根据来源 s，陈述 z 成立」。Tally 的 verify 闸门就是 AIS 的工程化：每句答案必须能在证据池里对上刻痕； 对不上，降级成纯引用原文的抽取式回答；连原文都没有，拒答。

    1.4 封闭世界契约

    Tally 的 v0.7 契约只有三条，却是整个系统成立的前提：

    1. 事实只来自内部 RAG 证据——LLM 的参数知识可以组织语言， 永远不产出事实；
    2. 工具白名单只有内部动作（search / metrics_table / derive）—— 永无浏览器、外部 API、模型生成的代码；
    3. 只有 verify:pass 的结构化事实进长期记忆。

    为什么封闭世界重要？开放世界里 verify 永远证伪不了「模型碰巧 知道」——答案对了，你不知道它是检索到的还是编得恰好对了。封闭 世界让「对账」变成可判定的问题。这也是 Tally 与 CRAG 这类 「检索不够就上网补」的路线（arXiv:2401.15884） 的根本分野：金融场景宁缺毋滥。

    1.5 双脑架构：一张图看全书

    离线：PDF/MD ─→ 文件名元数据 ─→ 页眉剥离 ─→ 表格感知分块 ─→ 数字归一化
                （SHA-256 指纹增量：增/改/删自适应）          ← 第 2、3 章
                     ↓
              SQLite（六表 + FTS5 双轨倒排）                   ← 第 4 章

在线（LangGraph 状态机）：
  问题 → understand（LLM 理解 + 规则守卫）                     ← 第 6 章
        → memory_probe → route（期间守卫）
        ├── 多跳信号 → plan（只删不造）→ agent_research（ReAct）← 第 10、11 章
        ├── heuristic → retrieve（双轨 FTS + RRF）→ grade ⇄ rewrite ← 第 5 章
        ├── trend → trend_research（确定性遍历 + 单季差分）
        └── other → refuse
        → generate（grounded，逐句带 [公司_报告期 第N页] 引用）  ← 第 7 章
        → verify_citations（覆盖率 <0.45 降级 / 无据拒答）       ← 第 8、9 章
                                                              ← 评测与边界：第 12、13 章

    同一张图、两个大脑：LLM 模式与零 key 的规则模式（heuristic）跑同一 套节点和闸门——heuristic 是可复现的回归基线，也是本书大部分实验的 确定性对照组。「workflow 与 agent 之间还有中间态」——Anthropic 那篇文章的谱系里，Tally 站在「engineered workflow 承重、局部 agentic」 的位置上，这是财报域刻意的选择：闸门必须确定，评估必须可回归。

    1.6 动手：跑通 + 第一次被拒答

    python -m tally.cli ask "欧科亿 2026 年半年度预计净利润多少"
# → 预计净利润 36,000 万元至 42,000 万元（约 3.60 亿元至 4.20 亿元）
#   [欧科亿_2026H1E 第1页]

python -m tally.cli ask "欧科亿 2030 年净利润预测"
# → 库里没有 2030 年期间的报告……对不上账，不硬答。

python -m tally.cli eval    # 七数据集 84 题评测，一条命令复现全部指标

    观察：拒答不是失败，是系统在告诉你「先对账」。注意拒答文案里 列出了库里现有的全部期间——拒绝也要拒绝得有用。
