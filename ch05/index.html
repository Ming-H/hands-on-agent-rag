    第 5 章 检索：双轨 FTS + RRF，以及「要不要 embedding」

    状态：v0.2 · 所属：第一部 知识入库 · 前置：第 4 章 ★ 本书最反共识的一章：词法饱和时，向量是净负贡献——用消融实验说话

    5.1 失败先行：字轨整段短语的坑

    v0.4 初版把字轨查询写成「空格整段短语」——"预计净利润多少" 作为 连续子串在原文里永远不存在（被年份、标点隔开）。答案块在字轨 零命中，融合排序崩塌。修复写进了 docstring：

    # tally/fts.py: char_expr
def char_expr(query: str) -> str:
    """字级轨道：≥2 字词 token 做 trigram 短语 OR（子串命中，跨词边界）。
    不能用空格整段短语——「预计净利润多少」在原文里被年份隔开，
    整段短语永远不命中。"""

    通用教训：换检索引擎时，查询语义的等价性要逐轨道验证。

    5.2 业界视角：检索模型谱系与混合检索

    背景速览

    RAG 检索的三大流派（决定了你要什么存储，呼应第 4 章）：

    流派 代表 强项 弱项
    稀疏/词法 BM25（FTS5/ES 内置）、SPLADE（arXiv:2107.05720） 精确词面、数字、专有名词；零训练 词面鸿沟（问法≠写法）
    稠密/语义 BGE 系列、OpenAI embeddings 同义改写、跨语言泛化 数字/口径混淆；要嵌入基建
    混合 + 融合 BM25 + dense → RRF 互补 两套索引成本

    RRF（Reciprocal Rank Fusion）是混合检索的业界默认融合法 （Cormack et al., SIGIR'09：论文、 作者站全文 PDF）：

    score(d) = \sum_{r \in R} \frac{1}{k + rank_r(d)},\quad k=60

    只用排名不用分数——不需要跨系统的分数可比性，实现三行。 Elasticsearch/Weaviate/LangChain 的 hybrid 检索都已内置 RRF。 进阶还有 rerank 层（cross-encoder 精排 top-20，如 BGE-reranker） 与晚期交互（ColBERT, arXiv:2004.12832）—— Tally 在 31 题真值集上词法已饱和（下文），这些层的增益前提不存在。

    5.3 双轨设计：两条腿各补一个盲区

    失败路径 兜底的轨道
    分词错误（专业术语被切碎） 字轨（trigram 子串命中，对分词免疫）
    词面鸿沟（问法 ≠ 写法） 词轨 + 查询扩展（营收→营业收入） 
    # tally/fts.py: search（RRF 节选）
    for ranking in rankings:                    # 词轨 / 字轨 /（可选）向量
        for rank, row in enumerate(ranking, start=1):
            cid = row[0] if not isinstance(row, str) else row
            rrf[cid] = rrf.get(cid, 0.0) + 1.0 / (60 + rank)

    词轨还做了小而关键的清洗（word_expr）：丢单字中文虚词—— 「的/年/亿」idf 极低，进 MATCH 只会稀释排序。融合不调权重—— 排名互补是免费的鲁棒性。

    5.4 重头戏：embedding 消融（D19）

    教科书说 RAG 要上向量。Tally 完整实现了向量第三路（bge-small-zh @ fastembed，同律 RRF），然后在 31 题人工核对真值集上消融：

    数据集 双轨 answer_hit 向量三路 answer_hit
    default 10 1.00 0.875
    agent 8 1.00 0.833
    innolight 31 1.00 0.926

    三连 1.00 = 词法双轨在此任务上已饱和——加第三路只可能持平或 变差。掉分机制值得细品：bge 的语义泛化把「同文档里语义相近但 口径不同」的块拉近，挤掉精确命中——被害题恰好全是为口径守卫 修过的类型（年报营收、同比增长、归因句）。一句话：在数字与口径 的精确匹配任务上，语义相近恰恰是风险而非收益。

    决策：默认关闭，TALLY_VEC=on 显式 opt-in。「用数据决定关掉 一个 feature」——比「又接了一个向量库」的含金量高得多。

    什么时候该开向量

    D19 的结论不是「向量没用」，是「在词法饱和 + 口径敏感的任务 上没用」。语义泛化问法（「为什么/怎么样/跨文档对比」）、词面 零重叠语料（口语问答社区）、跨语言检索——向量仍是正解。方法学 才是可迁移的：先建真值集，再跑消融，让数据替你选。

    5.5 消融方法学（可以抄走的部分）

    1. 固定对照组：heuristic 模式（零 LLM 方差）；
    2. 人工核对到分位的真值关键词；
    3. 一次只动一个变量；
    4. 不只看总分：被害题逐题分析（被害的都是哪类题？为什么？）；
    5. 结论写成决策记录（D19），默认行为跟着结论走。

    5.6 动手：读通向量路的接入代码（讲解型）

    本节的「实验」是读代码——嵌入全库在作者机上内存开销大（bge 模型加载 ~18s + 全库前向），权威数字以 D19 实测存档为准（5.4 的 表）。有闲置机器的读者可以跑 experiments/ch05-embedding-ablation.sh 复现，跑不了也不损失任何理解——三段代码就是全部故事。

    第一段：开关的两问分离（tally/embed.py）——「装没装」和「开没开」 是两个独立的问题，混在一起就会出现「没装依赖的机器上查询报错」：

    def installed() -> bool:
    """可选依赖是否在（CLI embed 建索引只看这个）。"""
    try:
        import fastembed  # noqa: F401
        return True
    except ImportError:
        return False

def enabled() -> bool:
    """查询路是否启用：显式 TALLY_VEC=on（opt-in）且依赖在。
    默认关闭是消融定的……向量第三路把语义相近但口径不同的块拉近、
    挤掉精确命中——0.875/0.833/0.926。"""
    return os.environ.get("TALLY_VEC") == "on" and installed()

    注意 enabled 的 docstring 把决策依据（消融数字）直接写进了代码—— 半年后有人想「顺手打开向量」时，会先撞见这段数字。

    第二段：查询侧排名——向量路不建新引擎，cosine 算完只交出一个 chunk_id 降序列表，与词法两轨同构：

    def ranking(con, docs, query, doc_filter, doc_scope, limit=24):
    """查询侧：embed query → doc 过滤后取库内向量 → cosine top。
    返回 chunk_id 相似度降序列表（三路 RRF 第三排名）；任何前置
    条件不满足返回 None（调用方退回双轨）。"""
    ...
    mat = np.frombuffer(b"".join(r[1] for r in rows),
                        dtype=np.float32).reshape(len(rows), DIM)
    norms = (mat * mat).sum(axis=1) ** 0.5
    sims = (mat / norms[:, None]) @ _query_vec(query)
    order = sorted(range(len(rows)), key=lambda i: -sims[i])[:limit]
    return [rows[i][0] for i in order]

    两个工程细节值得抄：①向量以 float32 blob 存在 SQLite vecs 表里 （512 维 ≈ 2KB/块，万级块 ~16MB——不引入独立向量库的容量代价）； ②返回 None 即静默退回双轨（第 5.2 节 fts.search 的 extra_ranking 参数）——CI 没装 fastembed 照常全绿，可选功能 不能变成部署门槛。

    第三段：融合同律——回看 5.3 节的 RRF 循环：rankings 列表里 词轨、字轨、向量轨地位完全平等，谁也不特殊。这就是「融合协议 不变」的含义：将来换 sqlite-vec/faiss，只动 ranking 的实现， 一行融合代码不改。
