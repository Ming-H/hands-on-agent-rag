## 2.1 失败先行：一个垃圾文件名的通关之旅

把 samples 里任一文件复制一份，改成 `20261009_某公司三季预告分析.md`
这种日期开头的名字，再摄取——收到 ⚠ 拒收。逐层看它为什么会伤害
整个系统：

```
坏文件名 → parse_filename 兜底拿「20261009」当公司名
        → doc_id = "20261009_MD" 入库
        → 检索"三季预告"时它可能命中（词面相关）
        → 答案引用 [20261009_MD 第0页] ——用户无法核对的幽灵引用
        → 永久占据语料（没有任何机制会淘汰它）
```

这是 Tally 的 P0.5 轮实测事故（「库内留过一具」原话写进了注释）。
教训是摄取层的第一军规：**元数据必须有确定性的来源，绝不靠模型
猜，也不靠模糊规则兜。**垃圾进、垃圾出——但更糟的是**半垃圾静默
地进**。

## 2.2 业界视角：PDF 解析的工具谱系

!!! note "背景速览"

    「PDF → 文本」远比想象复杂：PDF 是**页面描述格式**（画字符的
    坐标），不是文档格式（没有「段落」「表格」的语义单位）。业界
    工具分三代：

    | 代 | 代表 | 原理 | 适用 | 代价 |
    |---|---|---|---|---|
    | 文本层抽取 | pypdf、PyMuPDF | 读内嵌文本流+坐标 | 数字原生的 PDF | 表格结构丢失 |
    | 版面感知 | [Unstructured.io](https://unstructured.io)、pdfplumber | 视觉布局分区（栏/表/题注）| 混排文档 | 慢一个量级 |
    | 模型驱动 | Marker、MinerU、GROB | 视觉模型/OCR 重建结构 | 扫描件、复杂表格 | 最贵、有幻觉面 |

    选型法则：**能用文本层就别上版面分析，能上版面分析就别上模型**。
    每升一代，成本、延迟和不确定性各加一层——而摄取是离线高频操作，
    不确定性会被索引放大。Tally 的选择：pypdf（文本层）+ 表格感知
    分块（第 3 章，在切分层恢复结构）覆盖数字原生财报；扫描件
    **显式拒收**（2.5 节）而不是硬上 OCR——封闭世界里，不可靠的
    输入不如没有输入。

    延伸：LlamaIndex 的 [readers 生态](https://docs.llamaindex.ai)把
    各类解析器统一成接口；中文财报场景可关注 MinerU 的开源实现。

## 2.3 决策：文件名即元数据契约

巨潮资讯网的财报命名天然带着结构（`公司名_2026年半年度报告.pdf`），
券商研报也是（`日期-券商-公司-代码.pdf`）。Tally 的选择是**把这个
约定升格为契约**（`tally/ingest.py: parse_filename`）：

```python
# 研报：20260703-东吴证券-并行科技-920493-标题.pdf → (券商, 日期, 研报)
_REPORT_PAT = re.compile(r"^(\d{8})-([^-]+)-(.+)\.pdf$")

_PERIOD_PAT = [                                    # 文件名 → (period, kind)
    (re.compile(r"(\d{4})年年度报告"), "FY"),
    (re.compile(r"(\d{4})年半年度报告"), "H1"),
    (re.compile(r"(\d{4})年第一季度报告"), "Q1"),
    (re.compile(r"(\d{4})年第三季度报告"), "Q3"),
    (re.compile(r"(\d{4})年半年度业绩预告"), "H1E"),
    (re.compile(r"(\d{4})年第三季度业绩预告"), "Q3E"),
]
    # 兜底：主干必须是可读公司名（含 CJK）——日期开头的外部分析
    # 静默入库会产出 20261009_MD 这类垃圾 doc_id（污染检索与引用）；
    # 拒收让 cli 以 ⚠ 跳过（P0.5 实测库内留过一具）
    company = re.split(r"[__－-]", name)[0]
    if not re.search(r"[一-鿿]", company):
        raise ValueError(f"文件名解析不出公司名（主干={company!r}），拒收")
```

逐段读这段代码的三个设计：

1. **匹配顺序即优先级**：先试研报模式（8 位日期开头）、再试期间
   词表、最后兜底——兜底最严格（要求 CJK 公司名），宁可错杀不可
   放过。注意 `2026年半年度业绩预告` 排在 `2026年半年度报告` 之后
   是不行的吗？其实这里靠正则的完整匹配规避了前缀吞噬——`半年度
   报告` 的 pattern 不会匹配 `半年度业绩预告` 的文件名（「报告」
   ≠「业绩预告」），词表顺序在这里无歧义。**但同类前缀歧义在
   期间过滤那里是真坑**（第 6 章：`半年度` 包含 `年度`，substring
   匹配会让 FY 泄漏进 H1 查询——那里必须互斥有序匹配）。
2. **失败要贵**：`raise ValueError` 走 cli 的 ⚠ 报告链路——用户
   看得见、改得了（改文件名），而不是静默入库一具尸体。
3. **为什么不 LLM 猜**：①确定性——同一文件永远同一 doc_id，增量
   幂等依赖它；②零成本零延迟——摄取高频；③**猜错了你不知道**——
   文件名错了至少报错可见，模型猜错是静默的。业界有人用 LLM 给
   文档打元数据标签，适合低频富元数据场景；**身份类元数据
   （doc_id 键）必须确定性**，这是底线。

## 2.4 页眉剥离：一行空格打败逐字比对

PDF 抽取的正文页页带着「公司名 + 报告标题」的页眉。 naive 方案是
逐页硬编码删除前 N 行——对不同版式的报告立刻失效。Tally 的做法是
**文档级频率统计**：同一行（归一化后）在超过 30% 的页出现即判页眉。

关键坑在「归一化」——P2 事故实录（这是 Tally 三大事故复盘之一）：

> **现象**：页眉剥离对部分页失效，答案被「公司名+报告标题」噪声块
> 污染。
> **根因**：PDF 文本抽取的空格位置逐页漂移（`2026年` vs `2026 年`），
> 逐字相同的判定失效——出现频率被分散到两个「不同的行」，各自都
> 过不了 30% 阈值。
> **修复**：比对前 `re.sub(r"\s+", "", ln)` 剥尽空白，**且把数字也
> 剥掉**（页眉带着页码——「第 3 页」「第 4 页」不剥就页页不同）。

```python
# 归一化比对：剥空白 + 剥数字（页眉共享行与页码）
norm = re.sub(r"[\s\d]+", "", ln)
```

**通用教训（全书第二次出现，不会是最后一次）：文本相等性判定，
永远先定义归一化。**PDF 抽取的「视觉相同」与「字节相同」是两回事；
LLM 手写引用的格式漂移是同一问题的另一副面孔（第 7 章 D13）。

## 2.5 空文档闸门：扫描版 PDF 的静默失败

一份 232 页全扫描件（pypdf 抽不出文本）在 naive 管线里的完整旅程：

```
每页文本长度 < 20 → 全部被跳过
→ ingest_file 返回 0 个 chunk
→ 文档行写入 docs 表，manifest 记下指纹
→ 「成功」入库 ✓（没有任何报错）
→ 此后每次增量：指纹没变 → 跳过 → 永远不会重试
→ 库里躺着一具检索不可见、问答永空手的空壳
```

注意这个失败的**形态**：不是崩溃（崩溃会被发现），是静默成功——
最危险的一类。修复只需一行闸门（`ingest_file` 尾部）：

```python
    if not chunks:
        # 空文档闸门：0 块文档静默入库后 manifest 指纹锁死、永不重试，
        # 库里留一具问答永空手的空壳——显式失败让 cli 的 ⚠ 链路报告
        # （扫描版 PDF / 全空 md）
        raise ValueError(f"{path} 摄取出 0 块——疑似扫描版 PDF 或空文档，拒收")
```

**失败方式的选择也是设计**：显式抛错（用户可见可修：去 OCR）优于
入库「空」标记（静默债务）。这个模式会反复出现——好的系统让失败
**贵且可见**。

## 2.6 增量指纹：从 mtime 到内容哈希

摄取怎么知道哪些文件变了？`tally/source.py` 的答案演进了一轮：

```python
def _fingerprint(p: Path) -> str:
    """内容哈希指纹（流式读，1MB 块）——只看内容，与 mtime/ctime 无关。"""
    h = hashlib.sha256()
    with open(p, "rb") as fh:
        for block in iter(lambda: fh.read(1 << 20), b""):
            h.update(block)
    return f"sha256:{h.hexdigest()[:24]}"
```

初版用 `mtime_ns-size`（轻量、零 IO），被两个真实场景击穿：

| 场景 | mtime 指纹的行为 | 后果 |
|---|---|---|
| `cp -p` / `rsync -a` 保 mtime 改内容 | 指纹不变 → **漏更新** | 语料静默过期，检索答旧数 |
| `touch`（内容没变） | 指纹变了 → **假更新** | 无谓重摄取 |

换成 SHA-256 内容哈希后两洞皆堵，成本：双语料 36MB 全量哈希约
0.1 秒（流式读不吃内存）。配套的 three-way diff 在 `cli.py:
cmd_ingest`：`to_add`（新文件）/ `to_update`（指纹变）/ `to_delete`
（磁盘消失）——且**删除只对本根负责**（多根共存一库：samples/ 与
data/中际旭创/ 互不误删；这是 v0.4 多根摄取的实测教训）。

业界同构物：Airbyte / LlamaIndex 目录连接器的 path→fingerprint
账本——**增量摄取的幂等性，永远建立在「文件身份」的可信判定上**。

## 2.8 小结

- 元数据契约：身份类元数据（公司/期间）必须确定性来源——文件名
  契约优于 LLM 猜测，猜错是静默的；
- 页眉剥离靠文档级频率统计，**归一化先行**（剥空白+数字）；
- 空文档显式拒收：失败要贵、要可见；
- 指纹=内容哈希：增量幂等的根；漏更新比假更新更危险。
