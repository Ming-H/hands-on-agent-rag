## 9.1 知识：查询理解是个 NLU 问题——三子任务与三失败

用户 query 进系统的第一站是把自然语言变成结构化决策输入。这是
经典 NLU 的老问题，LLM 之前就有完整方法谱系：

| 子任务 | 例子 | 方法谱系（LLM 之前 → 之后）|
|---|---|---|
| **意图分类** | 「谁赚得多」→ compare | 规则词表 → 小分类器（fastText/SVM）→ LLM few-shot |
| **槽位填充** | 「欧科亿」「2026」「一季度」→ companies/period | 正则/CRF/NER → LLM 结构化抽取 |
| **查询改写** | 「营收」→「营业收入」；补全代词指代 | 同义词表 → LLM 改写（[LangChain 综述](https://python.langchain.com/docs/concepts/)：multi-query / HyDE / 分解）|

LLM 时代的主流是一次**结构化抽取**：prompt 里给 schema（枚举字段
+ 数组字段），模型吐 JSON。三子任务一次完成，且天然处理口语与
变体。**但把这类任务交给 LLM，三类高频失败**（与档位无关，频率
随档位降低、永不为零）：

| 失败 | 形态 | 下游灾难 |
|---|---|---|
| **槽位漏抽** | 多实体问句只抽中一个（「对比 A 和 B」抽到 A）| 对比退化成单查 |
| **意图漂移** | 同一问句多次采样出不同意图 | 走错管线（每次运行行为不同）|
| **参数幻觉** | 问「上半年」抽出 FY；问 Q1 抽出 H1 | 过滤失效，错文档洪水 |

**机理要讲透：LLM 输出是分布采样**。温度=0 只是取众数（贪心
解码），**不等于确定性**——三个来源：批处理里样本分组不同、
浮点归约顺序不同（GPU 并行求和不可结合）、服务端路由到不同
副本/量化版本。多轮自回归采样里，一个 token 位置的微小分岔
（两个近义 token 概率几乎相等时）会放大成完全不同的输出。所以
「同一问句三次三种意图」不是 bug，是采样本质。

**对策阶梯**（从便宜到贵）：

1. **schema 约束**：枚举字段把采样空间收窄到合法值（错误从
   「任意字符串」收窄到「合法枚举里选错」）；
2. **多次采样取多数**（自一致性，[Wang et al. 2022](
   https://arxiv.org/abs/2203.11171)）：同一问句采 k 次取众数
   ——成本 ×k，换来漂移概率指数下降；
3. **确定性规则复核**（本章主张）：对**规则可判**的字段（词表
   子串、枚举闭集、元数据对账）用规则复核模型输出；
4. **校准与置信**（进阶）：让模型输出置信度，低置信走保守路径
   ——注意 LLM 置信度未必校准（说 90% 未必九成对），需实测。

结论一句话：**LLM 的输出是建议，不是命令。**

## 9.2 知识：路由——最基础的 workflow 模式

**路由**（routing）：按输入分类分发到不同处理路径。Anthropic
把它列为工作流模式之首（[Building Effective Agents](
https://www.anthropic.com/engineering/building-effective-agents)）：
**LLM 分类，确定性代码分发**。学术对应 [Adaptive-RAG](
https://arxiv.org/abs/2403.14403)（NAACL'24）：按查询复杂度分流
no-retrieval / 单步 / 多步检索——分类器 + 分流规则，仅此而已；
其价值在实证：简单问题不检索反而更好（检索噪声伤害无检索可答
的问题）。

路由还有第三种形态在快速成熟——**成本路由**：不按意图、按「这道题
需不需要贵模型」。RouteLLM（[arXiv:2406.18665](
https://arxiv.org/abs/2406.18665)，UC Berkeley/LMSYS）用人类偏好
数据训练路由器，推理时在强弱两档间动态选择：基准实测**成本降
2× 以上而答案质量不掉**，且路由器换强弱模型对后仍保持判力（迁移
性——它学的是「什么题难」不是「哪个模型好」）。与本书案例的
双脑路由对照：Tally 按意图把单跳题挡在 agent 环外，就是成本路由
的规则版——**路由既管质量也管钱**。


由此画全书反复使用的**判定线**：

```text
这个环节该用 workflow 还是 agent？
  能预先枚举执行路径吗？
    能  → workflow（代码编排，LLM 只在节点里干活）——确定性、可测、便宜
    不能 → agent（LLM 决定控制流）——灵活，但每步误差复合，
           必须有界 + 步级观测（第 11 章）
```

路由天然在 workflow 一侧：意图是可枚举的闭集（metric/compare/
trend/summary/other），路径是有限条。但**意图是连续谱**——
「营收怎么样」是 metric 还是 trend？离散枚举必有边界带。工程
答案是**分类 + 升降级守卫**：分类器给初值，确定性规则把边界带
推回多数派（有趋势词才准进 trend），而不是追求完美分类器。

**守卫设计通则**：对每个抽取字段问「规则能不能确定性判定？」
——能（词表子串/枚举/元数据对账）就写守卫；语义判断与隐式信息
留给模型。守卫的验收用**白盒测试**：monkeypatch 掉 LLM、注入
故意错的输出、断言守卫纠正——LLM 不可测（每次不同），防线可测
（确定性）。这是「测防线不测模型」原则。

**期间/时间这类字段为什么不留给模型**：有词表可枚举（一季度/
Q1/一季报 → Q1）、元数据有真值（库里有哪些年份）——交给模型
等于把确定性问题随机化（第 1 章信任分级的字段级应用）。附带
一个高频坑：期间过滤用 substring 会泄漏——「半年度」包含
「年度」，问 H1 时 FY 文档命中——要**互斥有序匹配**（按长度
降序匹配到即停）；裸年份无期间词 → 默认全年报。

## 9.3 案例研究：Tally 的理解节点与八守卫

!!! abstract "案例研究：Tally（graph.py: understand / route）"

    **一次结构化抽取 + prompt 全文**（模型实际收到的完整文本，
    拼接重排）：`chat_json(UNDERSTAND_PROMPT, q)` 失败抛
    ValueError 退规则（trace 标 `understand:llm→fallback`）。

    ```text
    你是财报问答系统的查询理解器。从用户问题抽取 JSON：
    {"intent":"metric|summary|compare|other",
     "companies":["公司名"],"period":"H1|Q1|Q3|FY|","reason":"一句话"}

    规则：
    companies 原样取自问题中的公司名（没有则空数组）；
    period 按财报日历（一季度/一季报/Q1→Q1，半年度/中报/二季度→H1，
      三季→Q3，年度/年报/四季度→FY，仅提年份不提期间
      （如「2025 年营收」）也算 FY，未提及则空串）；
    intent：
      metric   = 问具体数字/指标/事实/原因/归因（需要检索证据句）
      trend    = 跨期趋势/多期对比；问投资建议也归 trend
      summary  = 要整体概览/总结全篇
      compare  = 对比多家公司
      other    = 闲聊或超纲

    注意「XX变动的原因」是 metric 不是 summary，
    「最近几个季度的趋势」是 trend 不是 summary。
    ```

    **prompt 四要点**（可迁移的写法）：**枚举白名单**写进 prompt
    （下游再防御性归一）；**口语映射表明说**（中报→H1——LLM 的
    日历知识不可靠，别赌）；**边界反例**钉最易混处（最后两行）；
    **失败兜底显式**（ValueError → 规则）。

    **守卫代码走读**（八条守卫全表见附录 D，注释即事故档案）：

    ```python
    # tally/graph.py: understand（守卫节选——每条对应一次实测事故）
    if u.get("intent") == "summary" and _wants_trend(q):
        u["intent"] = "trend"          # 趋势守卫：趋势问句判成 summary
    if len(rule_u["companies"]) > len(u.get("companies") or []):
        u["companies"] = rule_u["companies"]   # 公司漏检：规则子串补全
    if rule_u["period"]:
        u["period"] = rule_u["period"]         # 期间覆盖：规则非空即覆盖
    if u.get("intent") == "metric" and rule_u["intent"] == "trend":
        u["intent"] = "trend"          # 对称升级：模型自己差不出
                                      # Q4=FY−Q3（quarters 集 6 题全灭根因）
    ```

    每条守卫锚定一个白盒测试（`test_understand_period_override_
    and_trend_necessity` 等）——**守卫是事故的存款**。Tally 在
    0.8b 档的实测恰好集齐 9.1 的三类失败，是本章知识的天然例证。

    **期间守卫**（route 节点）：年份来自文档元数据（第 2 章契约
    的下游红利），语料没有该年份直接拒答并列出现有期间——
    **确定性元数据 → 确定性守卫**。`query_years` 连「15年」口语
    年份都解析（但必须后随「年」——否则金额里的数字被误当年份，
    实测踩过）。

### 演练：一道真实 query 过八守卫

「**欧科亿和海伦哲 2026 年上半年谁更能赚**」逐条过守卫（案例
实测行为，`-v` 可复现）：

```text
LLM 抽取（0.8b 实测形态）：{intent:"metric", companies:["欧科亿"],
                          period:"FY"}        ← 三处埋雷
守卫 2 公司漏检：规则子串找到两家 → companies 补为 ["欧科亿","海伦哲"]
守卫 5 期间覆盖：规则命中「上半年」→ period 改 "H1"（LLM 抽 FY 是幻觉）
守卫 4 意图守卫：≥2 公司 + 对比词「谁更能」→ intent 升 "compare"
结果：compare + 两家 + H1 → 进分解路径，各自检索各自过闸
```

三处雷一次全拆——**守卫带是串行过滤器**，每条只管自己的字段，
可测可加；没有一条试图「让模型变聪明」。

## 9.5 小结

- 查询理解 = 意图分类 + 槽位填充 + 改写；LLM 一次结构化抽取是
  主流，但三类失败（漏抽/漂移/幻觉）源于分布采样——温度=0 仍
  非确定（批分组/浮点归约/副本差异三来源）；
- 对策阶梯：schema 约束 → 自一致性（成本换稳定）→ 规则复核
  （规则可判字段）→ 校准置信（需实测）；
- 路由是最基础的 workflow（LLM 分类、代码分发）；意图连续谱用
  分类 + 升降级守卫；判定线：路径可枚举 → workflow；
- 守卫白盒验收：注入错误、断言纠正——测防线不测模型。

## 常见误区

**误区一：「模型够强就不需要守卫」。**守卫防「抖」不防「笨」——
采样本质决定了枚举字段出错率永不为零；守卫成本（几行规则）与
失效代价（整条管线走错）不成比例。

**误区二：「温度=0 就是确定性」。**只取众数，不消除批分组/浮点
归约/副本差异——要确定性，答案在规则与测试，不在解码参数。

**误区三：「意图分类一次搞定」。**连续谱必有边界带；分类 + 升
降级规则是工程解，完美分类器是伪需求。

**误区四：「期间/年份交给模型更智能」。**词表可枚举、元数据有
真值的东西交给模型 = 把确定性问题随机化。
