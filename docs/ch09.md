# 第 9 章 口径守卫：问扣非为什么不能答归母

> 状态：初稿 v0.1 · 所属：第二部 求证闸门 · 前置：第 8 章

## 9.1 失败先行：verify:pass(0.529) 的错答案

第 8 章留下的缝隙，具体长这样：问「扣除非经常性损益后的净利润」，
系统答了归母净利润 `1,582,876,128.67`——**这个数字真的在证据池里、
真的有出处**，引用覆盖率 0.529，verify 判 pass。闸门管「有出处」，
不管「对题」。

这类错误有个统一的名字：**口径混淆**。而且语义检索越是「好」，
这种错越严重——归母和扣非在向量空间里几乎是贴着的（都是净利润！）。
（回想第 5 章：D19 消融的被害题恰好全是口径题。）

## 9.2 五层防线：从拼块到评测

Tally 的答案是一层层修出来的，每层对应一类实测越界：

| 层 | 位置 | 防什么 |
|---|---|---|
| ① stitch_adjacent 拼块 | 检索后 | 标签与数值分家——拼不回去连「选哪行」都无从谈起 |
| ② 行级抽取 + 标签上下文 | trend pick | 「指标词后第一个大数」+ 前邻 20 字的口径检查 |
| ③ 配对口径降权 ×6 对 | answer.py | 问 X 时同胞指标 Y 的句子降权 0.3×（见下）|
| ④ caliber_mismatch 数值闸 | graph.py (D22) | 问具名口径→答案大数必须在该口径标签行里，否则降级 |
| ⑤ forbid_keywords | evals/*.json | 评测层反向断言：问扣非的答案不得出现归母的数 |

第③层的实现是六对「家族降权」，注释本身就是案例库：

```python
# tally/answer.py（节选——注释即实测档案）
# ① 问扣非：无「扣除/扣非」的净利润句是归母口径（茅台 2026H1 实测
#    445.17 亿散文句顶掉 44,464,207,646.01）
if (("扣非" in q_raw or "扣除非" in q_raw)
        and "净利润" in s and "扣除" not in s and "扣非" not in s):
    score *= 0.3
# ③ 问总收入：营业收入句是子口径不是总口径（真值 92,278,072,083.21
#    被营业收入行冒充，2026H1 p30）
if "总收入" in q_raw and "营业收入" in s and "总收入" not in s:
    score *= 0.3
```

注意设计取舍：**降权不跳过**——双口径问句（「扣非和归母差多少」）
仍要看到对方。规则惩罚的是「冒名顶替」，不是「同场出现」。

## 9.3 第⑤层：评测层的负向断言

单测层一直有负向断言（断言错数**不在**答案里），v0.7 后期把它上移
到 eval 层——`evals/dataset-innolight.json` 里两道扣非题：

```json
{
  "q": "中际旭创 2025 一季度扣除非经常性损益后的净利润多少",
  "expect_keywords": ["1,568,385,287"],
  "forbid_keywords": ["1,582,876,128"]
}
```

答案出现 forbid 的数（归母姊妹值）→ 该题判 miss，一票否决。
评测和防守共用同一套口径知识——这是「评测即测试」的微观样本
（第 12 章宏观展开）。

## 9.4 泛化的诚实：第三家公司进来要修多少规则？

六对降权是两家公司语料（中际旭创 + 贵州茅台）喂出来的。第三家
公司会带来新的口径家族吗？会的。但有两层兜底：①④层口径闸是
按「标签行验证」工作的，不依赖具体公司；②每对新家族只需一条
降权 + 一道 forbid 题——**修一台新电梯，不是重盖楼**。茅台零调参
9/9 是这个论断最好的证据（新公司进语料，九道真值题全对，没改
一行检索代码）。
