## 9.1 失败先行：0.8b 的三宗罪

本地小模型驱动查询理解的实测事故（每条都有测试锚定）：

| 死法 | 实测表现 | 下游灾难 |
|---|---|---|
| 漏抽公司 | compare 题抽对第一家、漏第二家 | 多跳对比退化成单公司问答 |
| 意图漂移 | 趋势问句判成 summary；同一 query 三次三种意图 | 答半篇文档残渣 |
| 期间幻觉 | 问「半年度」抽成 FY | 年报块洪水淹没目标期间 |

三条合起来是一个结论：**LLM 的输出是建议，不是命令。**大模型也
会犯（频率更低），架构上不能赌。

## 9.2 知识点：查询变换谱系、路由与 workflow/agent 判定线

检索前的查询处理，业界统称 query transformation（
[LangChain 概览](https://python.langchain.com/docs/concepts/)）：

| 技术 | 思路 | 典型场景 |
|---|---|---|
| 同义/术语扩展 | 问法→文档术语 | 领域黑话（营收→营业收入）|
| Multi-Query | LLM 生成多视角查询并行检索 | 提召回覆盖 |
| HyDE（[arXiv:2212.10496](https://arxiv.org/abs/2212.10496)）| 先生成假设答案再检索 | 零词面重叠 |
| 分解 Decomposition | 多跳问题拆子问题 | 跨年/多公司对比 |
| 路由 Routing | 意图分类→不同管线/索引 | 混合工作流 |

**路由是最基础的 workflow 模式。**Anthropic 把它列为工作流三件套
之首（[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)）：
**LLM 分类，确定性代码分发**。[Adaptive-RAG](https://arxiv.org/abs/2403.14403)
（NAACL'24）是它的学术版：按查询复杂度分流 no-retrieval / 单步 /
多步检索——understand 节点就是那个分类器，守卫就是分流规则。

由此可以画出全书反复使用的一条**判定线**：

```text
这个环节该用 workflow 还是 agent？
  能预先枚举执行路径吗？
    能  → workflow（代码编排，LLM 只在节点里干活）——确定性、可测、便宜
    不能 → agent（LLM 决定控制流：下一步查什么/调哪个工具）——灵活、
           但每一步误差会复合，必须有界 + 步级观测（第 11 章）
```

路由天然在 workflow 一侧：意图是可枚举的闭集，分发路径是有限条。
Tally 的 understand 节点是这个模式的完整实现，外加一层大多数教程
没写的部分——**对分类器本身的不信任**：小模型分类会抖动，规则
守卫把抖动压回语义正确的轨道。这也是 Adaptive-RAG 没写的那半句：
分类器错了怎么办。

## 9.3 本项目：一次结构化抽取 + 八条守卫



LLM 只做一件事——把问题抽成结构化三字段。调用本身只有一行：

```python
r = llmx.chat_json(UNDERSTAND_PROMPT, q)   # 失败抛 ValueError → 规则兜底
```

关键是 `UNDERSTAND_PROMPT` 写了什么。下面是**模型实际收到的完整
文本**（源码为多行字符串拼接，内容与此逐字一致，仅为可读性重排）：

```text
你是财报问答系统的查询理解器。从用户问题抽取 JSON：
{"intent":"metric|summary|compare|other",
 "companies":["公司名"],"period":"H1|Q1|Q3|FY|","reason":"一句话"}

规则：
companies 原样取自问题中的公司名（没有则空数组）；
period 按财报日历（一季度/一季报/Q1→Q1，半年度/中报/二季度→H1，
  三季→Q3，年度/年报/四季度→FY，仅提年份不提期间
  （如「2025 年营收」）也算 FY，未提及则空串）；
intent：
  metric   = 问具体数字/指标/事实/原因/归因（需要检索证据句）
  trend    = 跨期趋势/多期对比；问投资建议也归 trend
  summary  = 要整体概览/总结全篇
  compare  = 对比多家公司
  other    = 闲聊或超纲

注意「XX变动的原因」是 metric 不是 summary，
「最近几个季度的趋势」是 trend 不是 summary。
```

prompt 设计四要点：①**枚举白名单**写在 prompt 里（intent/period
的合法值），下游再做防御性归一；②**口语映射表**（中报→H1）——
LLM 的日历知识不可靠，明说；③**边界样例**（「变动的原因」是
metric 不是 summary）——用反例钉住最易混的边界；④失败抛
ValueError → 规则兜底（`understand:llm→fallback` 的 trace 标记）。

然后规则守卫逐条复核（`tally/graph.py: understand`，注释即事故
存档）：

```python
# 趋势守卫：小模型实测把趋势问句判成 summary（单文档残渣）
if u.get("intent") == "summary" and _wants_trend(q):
    u["intent"] = "trend"
# 公司漏检守卫：规则的子串匹配是确定性的，LLM 漏抽一家
# 会让 compare 退化成单公司 metric（samples 实测哪家题）
if len(rule_u["companies"]) > len(u.get("companies") or []):
    u["companies"] = rule_u["companies"]
# period 覆盖：query 有明确期间词时规则是确定性子串匹配，
# LLM 抽取实测会稳定抽错（「第一季度」→H1）——规则非空即覆盖
if rule_u["period"]:
    u["period"] = rule_u["period"]
# 对称升级（差分信号）：「第二/四季度」规则层判 trend（差分要走
# 确定性遍历+derive），小模型判 metric 进 agent 环——模型自己差不出
# Q4=FY−Q3，quarters 集 6 道派生题全灭的根因
if u.get("intent") == "metric" and rule_u["intent"] == "trend":
    u["intent"] = "trend"
```

八条守卫的全表（防的事故 → 动作）：

| # | 守卫 | 防的事故（实测）| 动作 |
|---|---|---|---|
| 1 | 趋势守卫 | 趋势问句判 summary | summary→trend |
| 2 | 公司漏检 | compare 漏抽一家 | 规则子串结果补全 |
| 3 | 公司纠偏 | 抽出语料外幻觉公司 | 回退规则名单 |
| 4 | 意图守卫 | 「哪家赚得多」判 metric | ≥2 公司+对比词→compare |
| 5 | 期间覆盖 | 「半年度」抽成 FY | 规则非空即覆盖 |
| 6 | trend 必要条件 | 「预计…多少」幻觉成 trend | 无趋势词降级（目标用规则意图）|
| 7 | 对称升级 | 单季差分题进 agent 环全灭 | 规则判 trend 则升级 |
| 8 | 股价/涨跌拒答 | 拿财报数字答行情 | 归 other 拒答 |

设计原则只有一条：**规则是确定性的地方，规则赢**（公司名子串、
期间词表、趋势词表）；语义判断和隐式期间留给模型。「LLM 提议、
确定性裁决」——与 Anthropic 的 workflow 哲学同向，但把它落到了
字段级。

## 9.4 本项目：期间守卫——年份不靠模型

```python
# tally/graph.py: route（节选）
q_years = query_years(q)          # 含「15年」→2015 口语年份
have_years = {d.period[:4] for d in corpus.docs.values() if d.period[:4].isdigit()}
if q_years and not (q_years & have_years):
    return {**state, "answer": f"库里没有 {…} 年期间的报告（现有期间：{…}）。"
            f"对不上账，不硬答。", "verdict": "refused", ...}
```

两个细节：①`query_years` 连「15年」这种口语年份都解析（但必须
后随「年」——否则「增加 35,922.46 万元」里的数字会被误当年份，
实测踩过）；②年份来自**文档元数据**（第 2 章文件名契约的下游
红利）。确定性元数据 → 确定性守卫，层的红利会延迟兑现。

另一个易踩坑（v0.4 轮实测）：期间过滤用 substring 会泄漏——
「半年度」包含「年度」，问 H1 时 FY 文档也命中。修复是**互斥有序
匹配**（`period_hints` 按长度降序匹配到即停）。外加 D18：裸年份
无期间词 → 默认 FY。

## 9.6 小结

- 路由的正确形态：LLM 提议（结构化抽取）、确定性裁决（规则守卫）；
  路由在 workflow/agent 判定线的 workflow 一侧；
- prompt 四要点：枚举白名单/口语映射/边界反例/失败兜底；
- 八守卫每条对应一次实测事故——守卫是事故的存款；
- 年份与期间来自元数据与词表，永不来自模型；
- 白盒测试：注入错误输出，验证纠正——不测模型，测防线。

## 常见误区

**误区一：「模型够强就不需要守卫」。**守卫防的不是「模型笨」是
「模型抖」——同一 query 三次三种意图的实测发生在 0.8b，但任何
档位的输出都是分布采样，结构化抽取的**枚举字段**出错概率永不为
零。守卫的成本（几行确定性规则）与失效的代价（整条管线走错），
这笔账怎么算都值得。

**误区二：「意图分类一次搞定」。**真实用户的意图是连续谱
（「营收怎么样」是 metric 还是 trend 还是 summary？），离散枚举
必然有边界带。工程答案是**分类 + 升降级规则**：分类器给初值，
词表守卫把边界带推回多数派——而不是追求一个完美分类器。

**误区三：「期间/年份让模型判断」。**这是最典型的「看起来智能
实际上危险」：期间判断有词表可枚举（确定性），年份在文档元数据
里有真值（对账源）。两者都交给模型等于把确定性问题随机化——
第 1 章信任分级的字段级应用。
