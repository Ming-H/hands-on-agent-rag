## 9.1 知识：查询理解是个 NLU 问题——三个子任务，三类失败

用户 query 进系统的第一站是把自然语言变成结构化决策输入。经典
NLU 把它拆成三个子任务：

| 子任务 | 例子 | 方法谱系 |
|---|---|---|
| 意图分类 | 「谁赚得多」→ compare | 规则词表 → 小分类器 → LLM few-shot |
| 槽位填充 | 「欧科亿」「2026」「一季度」→ companies/period | 正则/NER → LLM 抽取 |
| 查询改写 | 「营收」→「营业收入」；补全指代 | 同义词表 → LLM 改写（[LangChain 综述](https://python.langchain.com/docs/concepts/)：multi-query/HyDE/分解）|

LLM 时代的主流做法是一次结构化抽取（prompt 里给 schema，模型吐
JSON）。**把这类任务交给 LLM，三类高频失败**（与档位无关，频率
随档位降低但永不为零）：

| 失败 | 形态 | 下游灾难 |
|---|---|---|
| 槽位漏抽 | 多实体问句只抽中一个 | 对比退化成单查 |
| 意图漂移 | 同一问句多次采样出不同意图 | 走错管线 |
| 参数幻觉 | 问「上半年」抽出全年 | 过滤失效，错文档洪水 |

**机理：LLM 输出是分布采样**。温度=0 只是取众数，**不等于确定性**
——批处理切分、浮点归约顺序、服务端路由都会让「同一问句」产生
不同输出；多轮自回归采样里，一个 token 的分岔就放大成完全不同的
答案。已知对策从便宜到贵：结构化 schema 约束（枚举字段收窄采样
空间）、多次采样取多数（自一致性，[Wang et al. 2022](
https://arxiv.org/abs/2203.11171)）、以及本章的主张——**对可
判定的字段用确定性规则复核**。结论一句话：**LLM 的输出是建议，
不是命令。**

## 9.2 知识：路由是最基础的 workflow 模式

**路由**（routing）：按输入分类分发到不同处理路径。Anthropic 把
它列为工作流模式之首（[Building Effective Agents](
https://www.anthropic.com/engineering/building-effective-agents)）：
**LLM 分类，确定性代码分发**。学术版是
[Adaptive-RAG](https://arxiv.org/abs/2403.14403)（NAACL'24）：按
查询复杂度分流 no-retrieval / 单步 / 多步检索——分类器 + 分流
规则，仅此而已。

由此可画全书反复使用的一条**判定线**：

```text
这个环节该用 workflow 还是 agent？
  能预先枚举执行路径吗？
    能  → workflow（代码编排，LLM 只在节点里干活）——确定性、可测、便宜
    不能 → agent（LLM 决定控制流）——灵活，但每步误差复合，
           必须有界 + 步级观测（第 11 章）
```

路由天然在 workflow 一侧：意图是可枚举的闭集，路径是有限条。
意图分类器错了怎么办？——**分类 + 升降级规则**：分类器给初值，
确定性守卫把边界带推回多数派，而不是追求一个完美分类器（用户
意图本是连续谱，「营收怎么样」是 metric 还是 trend？离散枚举
必然有边界带）。

**护栏设计通则**（LLM 提议、规则裁决）：对每个抽取字段问「规则
能不能确定性判定？」——能（词表子串、枚举闭集、元数据对账）就
写守卫；语义判断和隐式信息留给模型。守卫的验收用**白盒测试**：
monkeypatch 掉 LLM、注入故意错的输出、断言守卫纠正——LLM 不可
测，防线可测。

## 9.3 案例研究：Tally 的理解节点与八守卫

!!! note "案例研究：Tally（graph.py: understand / route）"

    **一次结构化抽取**：`chat_json(UNDERSTAND_PROMPT, q)` 吐三字段
    （intent 枚举/companies/period），失败抛 ValueError 退规则
    （trace 标 `understand:llm→fallback`）。prompt 四要点：枚举
    白名单写进 prompt、口语映射表明说（中报→H1——LLM 的日历知识
    不可靠）、边界反例钉最易混处（「变动的原因」是 metric 不是
    summary）、失败兜底显式。（prompt 全文见附录 D。）

    **八条守卫**（全表见附录 D；注释即事故档案），代表四条：

    | 守卫 | 防的实测事故 | 动作 |
    |---|---|---|
    | 公司漏检 | compare 漏抽第二家→退化单查 | 规则子串结果补全 |
    | 期间覆盖 | 「半年度」抽成 FY | 规则非空即覆盖 |
    | 对称升级 | 单季差分题被判 metric 进 agent 环全灭（模型自己差不出 Q4=FY−Q3）| 规则判 trend 则升级 |
    | 趋势守卫 | 趋势问句判成 summary | summary→trend |

    **期间守卫**：年份来自**文档元数据**（第 2 章契约的下游红利），
    语料没有该年份直接拒答（列出现有期间）——确定性元数据 →
    确定性守卫。配套实测坑：期间过滤不能 substring（「半年度」
    包含「年度」，FY 会泄漏进 H1 查询）——互斥有序匹配。

    Tally 的实测（0.8b 档）恰好集齐 9.1 的三类失败，每条守卫锚定
    一个白盒测试——守卫是事故的存款。

## 9.5 小结

- 查询理解 = 意图分类 + 槽位填充 + 改写；LLM 抽取的三类失败
  （漏抽/漂移/幻觉）源于分布采样——温度=0 也不是确定性；
- 路由是最基础的 workflow：LLM 分类、代码分发；意图连续谱用
  分类 + 升降级守卫处理，不求完美分类器；
- 判定线：路径可枚举 → workflow；护栏通则：规则可判的字段用
  规则复核（LLM 提议、规则裁决）；
- 守卫用白盒测试验收：注入错误输出、断言纠正。

## 常见误区

**误区一：「模型够强就不需要守卫」。**守卫防的不是「笨」是
「抖」——任何档位的输出都是分布采样，枚举字段出错率永不为零。
守卫的成本（几行确定性规则）与失效代价（整条管线走错）怎么算
都值得。

**误区二：「意图分类一次搞定」。**意图是连续谱，离散枚举必有
边界带。工程答案是分类 + 升降级规则，不是更大的分类器。

**误区三：「期间/年份这类字段让模型判断更显智能」。**有词表
可枚举、元数据有真值的东西交给模型，等于把确定性问题随机化——
信任分级（第 1 章）的字段级应用。
