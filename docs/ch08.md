## 8.1 知识：选型五维与三种接入形态

模型选型是五个维度的联立求解，不是「哪个最强」：

| 维度 | 问什么 | 权衡要点 |
|---|---|---|
| 任务 | 理解、生成还是工具调用？ | 结构化抽取对小档位更友好；长叙述对大档位敏感 |
| 能力 | 档位够不够过你的闸门？ | 有闸门兜底时，档位只影响「讲得好不好」（第 7 章两极端已证）|
| 成本 | 单价 × 调用数 × token 数 | **agent 循环一次问答 5–10 次调用**——放大系数选型时就算 |
| 延迟 | p50/p95/p99 与长尾 | 远端长尾 20s+ 真实存在——超时与重试是必需品不是优化 |
| 数据边界 | 语料/问题能出域吗？ | 内部文档/合规场景，云端选项直接出局 |

落到接入形态是三叉树：

```text
数据能出域吗？──不能──→ 公司级自托管（vLLM + 开源权重）
      │                  吞吐与数据都不妥协；代价：运维推理服务
      └─能─→ 要零成本/离线/不出机？
               ├─是→ 本地（Ollama）——档位受本机算力限制
               └─否→ 云端 API——最强能力；代价：成本/长尾/出域
```

**vLLM 为什么让自托管成立**（[arXiv:2309.06180](
https://arxiv.org/abs/2309.06180)）：PagedAttention 把 KV cache
像操作系统页表一样管理——显存碎片大幅减少、并发吞吐逼近商用
服务；配合 continuous batching（新请求插队进正在跑的批次），
单卡能撑起团队级服务。「公司数据不能出域 + 团队共用」的场景，
vLLM + 开源权重是标准答案。

**OpenAI 兼容协议是事实标准**：2024–2025 年几乎所有服务商
（DeepSeek/智谱/vLLM/Ollama/各大云）都提供兼容的
`/v1/chat/completions`。工程含义：**接入层写一次，换服务商改
一个 base_url**。例外两类（行为差异大到必须特殊对待）：本地
Ollama 的兼容层会**静默丢参数**（原生 `/api/chat` 才有完整控制，
见 8.4 案例 D7）；Anthropic Messages 协议（thinking 预算语义
不同、工具调用块结构不同）。

**结构化输出三条路线**：

| 路线 | 机制 | 可靠性 | 代价 |
|---|---|---|---|
| prompt 约束 | 「只输出 JSON」+ few-shot | 最低：围栏包裹、前后夹说明、字段漂移 | 零依赖 |
| JSON mode / function calling | 服务端保证合法 JSON / 按 schema 出参数 | 高（协议层）| 依赖服务商 |
| 受限解码 | 解码器层约束语法（[outlines](https://arxiv.org/abs/2307.09702)、GBNF）——非法 token 根本采不到 | 最高 | 要控制解码器；云 API 给不了 |

工程正解是**三层叠**：协议层保证（能用就用）+ 防御性解析（剥
围栏/取平衡块，失败抛异常）+ 调用点规则兜底（降级而非崩溃）。
不追求受限解码——因为兜底存在，解析失败的代价是降级不是事故。
「可靠性靠结构不靠解码」。

**工具调用协议要点**（设计原则在第 11 章）：严格协议要求
assistant 的 `tool_calls` 项带 `id + type`、`arguments` 是 **JSON
字符串**（不是对象）、tool 消息回指 `tool_call_id`。内部用宽松
格式、边界做归一化是常见解法（见案例）。

## 8.2 知识：推理工程面与成本模型

接入层不只是「调通」，是一组生产参数的工程：

- **超时与重试**：无超时的调用会被长尾拖到半分钟。起点：SDK 层
  60s 超时 + 重试 1 次——**重试是止血不是治病**，超过 1 次说明
  该降级了（与全书「纠正环有界」同一纪律）；
- **批处理（Batch API）**：离线评测/语料加工走批通道——半价
  量级、分钟到小时级返回。评测集跑批与在线单问走不同通道是
  免费的省钱；
- **流式（streaming）**：首 token 延迟决定体感——「等 15 秒出
  全文」与「立刻开始读」是两种产品。注意：流式下做输出校验要
  拼完再验（verify 吃的是完整答案）；
- **提示缓存（prompt caching）**：system prompt + 检索上下文的
  相同前缀命中缓存，成本与延迟双降（各家普遍支持，命中率计费）。
  排版纪律从风格变成省钱：**稳定内容放前面、变化内容放后面**；
- **成本模型**：每问成本 = Σ 各调用（token_in×价_in + token_out×
  价_out）。没有**调用账本**（每问几次调用、各多少 token、命中
  缓存多少）的系统不知道自己多贵；agent 放大系数（5–10×）要在
  选型阶段进五维表。

**thinking 与温度的分层纪律**。思考预算（reasoning tokens）普遍
**计入输出预算**——开思考可能吃光 max_tokens、正文为空；「常思」
模型尤其。纪律分层：**结构化调用永远关**（廉价枚举任务，思考只
花钱）、**生成路径按需**（小档位开思考延迟翻数倍且收益低——
生成垮了由 verify 降级兜底；强档位开思考叙述质量可期——实测再
说）。温度同构：凡是要确定性的地方（抽取/评分/路由）
`temperature=0`，叙述生成小温度（0.1–0.3）。

**通道行为必须实测**：「兼容协议」≠ 参数语义一致——每换一个
通道，关键参数（结构化输出、工具调用、思考预算、温度）都要
验证生效。清单化：接入新通道 = 跑一遍「参数生效验证 + 评测集
对照」（三档对比实验，8.4）。

**显式失败优于半成品**：接入层第一美德不是全覆盖，是失败得明
明白白。没实现的组合显式 `NotImplementedError` + 走兜底路径
（答案同闸）；一个「能调通但参数被静默吞掉」的通道是定时炸弹。

## 8.3 案例研究：Tally 的 llm.py

!!! note "案例研究：Tally（llm.py，约 290 行）"

    **通道判定 = 两个纯函数**——没有配置项没有「用户选」，host
    与路径即协议：

    ```python
    # tally/llm.py（判定核心）
    def _use_local() -> bool:
        return "localhost" in _base_url() or "127.0.0.1" in _base_url()

    def _use_anthropic() -> bool:
        return "/api/anthropic" in _base_url()   # Messages 协议判定
    ```

    全部配置五个环境变量（`TALLY_LLM_API_KEY / BASE_URL / MODEL /
    MAX_TOKENS / THINKING`），换档只改 `TALLY_LLM_MODEL` 一行。
    密钥纪律：key 只进 `.env`（gitignored），环境变量优先——
    conftest 剥 key 封网，让「测试永不真调 LLM」成为可能。

    **D7 三实测**（通道行为必须实测的现场，DESIGN-v0.5）：
    ①Ollama 的 `/v1` 兼容层**静默吞 `think` 参数**——本地通道
    绕过 SDK 直连原生 `/api/chat`；②Qwen3.5 的 `/no_think` 软开关
    已死（prompt 写什么都没用，开关在 API 参数）；③thinking 计入
    max_tokens——Anthropic 通道 512 预算被思考吃光正文为空，该
    通道预算自动 ×8。由此沉淀分层纪律：结构化永远关、本地默认关
    （0.8b 开思考延迟 ×5：14s vs 3s 实测）；温度 0（结构化）/
    0.2（生成）。

    **防御性解析**（三层叠的第二层）：

    ```python
    # tally/llm.py: _parse_json（骨架）
    fence = re.search(r"```(?:json)?\s*(.+?)\s*```", s, re.S)
    if fence:
        s = fence.group(1)          # 剥 markdown 围栏
    start = s.find("{")
    # …花括号深度平衡扫描，取第一个完整对象；失败抛 ValueError
    ```

    **消息归一化**（宽松格式 ↔ 严格协议，第三层）：
    `_normalize_tool_messages` 给 tool_calls 按会话位置确定性生成
    id（call_1..call_N）、arguments 序列化为 JSON 字符串、tool
    消息回指 tool_call_id——**不就地污染入参**（本地通道继续用
    宽松格式）。v0.7.1 靠它接通远端 function calling，上层 agent
    环零改动。超时治理：SDK `timeout=60.0, max_retries=1`。

    **显式失败**：Anthropic 通道 tools 未接 → 显式
    NotImplementedError → agent 环走固定管线兜底。远端实测
    （glm-5.3，agent 集 8 题）：22 次调用 dup=0、waste_rate 0.227、
    两道 compare 被 0.45 阈值降级抽取式仍全对——闸门在真实远端
    生成路径上的实弹证明（第 11 章续）。

## 8.5 小结

- 选型五维 × 三形态；vLLM（PagedAttention + continuous batching）
  让自托管成立；OpenAI 兼容是事实标准，例外两类必须实测；
- 结构化输出三层叠（协议保证/防御解析/兜底）；工具调用协议的
  严格性靠边界归一化消化；
- 推理工程面：超时重试（1 次封顶）/批处理分流/流式体感/提示缓存
  （稳定前置）/调用账本——agent 放大系数选型就算；
- thinking 与温度按确定性分层；显式失败优于半成品；
- 换通道 = 参数生效验证 + 评测对照，不是「能调通」。

## 常见误区

**误区一：「接最强模型再说」。**通道/密钥/参数硬编码进业务代码，
每次换档都是回归测试；五环境变量 + 自动判定，换档是运维动作。

**误区二：「兼容协议 = 行为一致」。**`/v1` 能调通 ≠ 参数生效——
think 被静默吞是实例。每通道做参数生效验证。

**误区三：「解析失败用更长的 prompt 修」。**更长 prompt 降频率不
改形态；三层叠才是结构解。

**误区四：「流式输出更高级，全上」。**流式改善体感，但校验、
工具调用循环、评测都要完整输出——什么路径流式、什么路径等全，
是产品决策不是技术炫耀。
