# 第 4 章 存储选型：SQLite FTS5 vs 向量库 vs ES

> 状态：初稿 v0.1 · 所属：第一部 知识入库 · 前置：第 3 章

## 4.1 失败先行：1.8GB 内存与 117 秒重建

Tally 的 v0.3 用自研**内存倒排**：60.7 万 chunk 常驻 1.8GB，每次增量
摄取后全量重建索引 117 秒。线性外推全 A 股五年（3,000 万块）需要
90GB 内存——本机差一个数量级。这是容量墙撞上来的真实声音。

## 4.2 决策方法：实测表，不是信仰

选型备忘（被否决的备选和理由，与选中的一样重要）：

| 备选 | 否决理由 |
|---|---|
| Elasticsearch | 单机 JVM 是负资产；本场景单查询方 |
| 向量库（FAISS/milvus） | 增益未证明（第 5 章消融实测为净负）|
| 自研磁盘倒排 | 重复造 FTS5 的轮子 |
| **SQLite FTS5 双虚拟表** | 磁盘倒排，容量与内存解耦，零运维 |

换 FTS5 的同机同库验收（这就是决策依据的形态——**一张实测表**）：

| 指标 | v0.3 内存倒排 | v0.4 FTS5 |
|---|---|---|
| 启动时间 | 117s（重建）/ 5s（pickle 热启） | **0.05s** |
| 内存常驻 | 1.8 GB | **0.03 GB** |
| 检索延迟（稳态） | 9 ms | 39 ms |
| 增量摄取 | ~3 min（含重建） | **0.8 s** |
| 全库 retrieval@3 | 0.75 | **0.875** |

延迟 9→39ms 是付的代价，换来容量解耦与免重建增量——**工程选型
就是选你愿意付哪笔代价**。

## 4.3 六表 schema 与唯一写入口

```
docs / chunks / fts_w / fts_c / manifest / verified_facts   (+ 可选 vecs/vecmeta)
```

两条铁律（都由 `tally/store.py` 的真实事故换来）：

**铁律一：Store 是唯一写入口。** 任何绕过 Store 直写 SQL 的路径，
迟早造出 fts rowid 与 chunks.rowid 的错位。

**铁律二：更新 = drop-then-insert，且必须同一事务。** P1 事故：
`INSERT OR REPLACE` 会给 chunks 换新 rowid，旧 rowid 的 FTS 行不被
覆盖——库里留下「幽灵块」，检索命中已删除的内容。修复演进两轮：
先改成先删后插；后来又发现 drop 和 insert 分属两个事务，中间崩溃
= 文档消失且指纹未变永不重试——最终合并为单事务：

```python
# tally/store.py: add_doc（节选）
    with con:
        self._drop_doc_tx(con, doc.doc_id)     # 清旧：同事务，不自行提交
        con.execute("INSERT OR REPLACE INTO docs VALUES (?,?,?,?,?,?)", ...)
        for c in chunks:
            cur = con.execute("INSERT OR REPLACE INTO chunks VALUES (?,?,?,?,?,?,?)", ...)
            rowid = cur.lastrowid
            con.execute("INSERT INTO fts_w(rowid, content_w) VALUES (?,?)", ...)
            con.execute("INSERT INTO fts_c(rowid, content_c) VALUES (?,?)", ...)
```

对应的永久回归测试：`test_readd_after_drop_no_ghost`（幽灵块）和
`test_add_doc_failure_is_atomic`（中途抛错后旧文档完好）。

## 4.4 PRAGMA 是连接级的（容易踩的坑）

```python
# tally/fts.py
_PRAGMAS = ("PRAGMA cache_size=-200000", "PRAGMA mmap_size=1073741824",
            "PRAGMA temp_store=MEMORY")
# 注意 sqlite 的 PRAGMA 按连接生效——必须每次连接都设，不能做全局一次性。
```

SQLite 的 PRAGMA 大多**不持久**（WAL 除外）——新开连接忘了设，
性能 silently 掉一个量级，且不报错。这类「静默性能回归」只能靠
代码审查和注释防御。

## 4.5 动手实验

```bash
sqlite3 tally.db ".schema chunks"        # 六表结构 + idx_chunks_doc 索引
sqlite3 tally.db "EXPLAIN QUERY PLAN
  SELECT chunk_id FROM chunks WHERE doc_id='海伦哲_2026Q1'"
# 预期：SEARCH chunks USING INDEX idx_chunks_doc——索引命中
# （无索引时全表扫 60.7 万行实测 31.8ms → 建索引后 <0.1ms）
```
