## 4.1 知识：存储选型——三维与判定三问

「向量库」只是 RAG 存储的一个子集。按查询能力看全景：

| 类别 | 代表 | 查询能力 | 运维形态 | 何时选 |
|---|---|---|---|---|
| 嵌入式向量库 | FAISS、[Chroma](https://www.trychroma.com) | ANN 近邻 | 库/进程内 | 原型、单进程 |
| 服务型向量库 | [Milvus](https://milvus.io)、[Qdrant](https://qdrant.tech) | ANN+过滤+复制 | 集群 | 多查询方/大数据量 |
| 数据库扩展 | [pgvector](https://github.com/pgvector/pgvector) | SQL+向量 | Postgres 生态 | 已有 PG 的团队 |
| 全文检索 | ES/OpenSearch、Meilisearch、SQLite FTS5 | BM25 词法 | 服务/嵌入 | 精确词面/数字任务 |
| 混合引擎 | Weaviate | 词法+向量+RRF 内置 | 服务 | 混合检索一步到位 |
| 图数据库 | Neo4j（GraphRAG）| 关系遍历 | 服务 | 多跳实体推理 |
| 结构化 | SQLite/Postgres/Mongo | SQL/文档 | 全形态 | 一切的底座 |

三个维度比「哪家向量库好」更重要——**查询能力 × 运维预算 ×
容量模型**。落到「内存倒排 vs 全文索引 vs ES vs 向量库」这道具体
题，判定三问：

1. **容量算术**：索引必须装进内存吗？能不能落盘？（块数 × 向量
   维度 × 4 字节——先算，再谈感觉）；
2. **增量频率**：每次写入后索引要不要全量重建？高频增量 × 全量
   重建 = 架构性死锁；
3. **进程模型**：单机单用户还是多查询方？服务型的运维链（部署/
   监控/升级）是不是负资产？

**先有查询需求，再有存储选型**——第 5 章的消融会告诉你你的任务
到底需要什么查询能力；反过来选就是拿着锤子找钉子。

## 4.2 知识：事务边界与数据不变量是设计决定

**ACID 的 A（原子性）不是数据库白送的，是「你把哪些操作圈进同一
个事务」的设计决定。**经典陷阱：更新 = 先删后插，若删除和插入
分属两个事务——中间的崩溃窗口就是数据消失的窗口（删已提交、插
没发生、账本指纹未变 → 永不重试）。正解：把「清旧 + 写新」圈进
**同一个事务**，要么全在，要么全不在。

**每个存储系统都有它的「rowid 对齐」类不变量**——正文与索引的
一致性约定。三个通用结论：

1. **唯一写入口**：所有写操作经一个模块（一个事务边界、一份不变
   量维护逻辑）——绕过它的直写路径迟早造出不一致，而索引不一致
   的表现是**检索命中已删除的内容**，不报任何错；
2. **影子索引模式**：索引只存索引化文本，正文只有一份事实——
   一份数据多个索引视图，重建索引不搬数据；
3. **静默性能回归**：很多引擎的性能参数按连接/会话生效而非持久
   ——新开连接忘了设，性能掉一个量级且无报错。对策是注释里的
   警告 + 集中一处每次连接都设，靠测试拦不住这类回归。

验证索引是否真的被命中：用执行计划工具（SQLite 的
`EXPLAIN QUERY PLAN`、Postgres 的 `EXPLAIN ANALYZE`）——「建了
索引」和「索引被命中」是两件事，全表扫描 60 万行与索引命中差
五个数量级。

## 4.3 案例研究：Tally 的六表与幽灵块事故

!!! note "案例研究：Tally（store.py / fts.py）"

    **选型经过**：v0.3 用自研内存倒排——60.7 万块常驻 1.8GB、
    每次增量后全量重建 117 秒（`--watch` 每 60 秒一同步，永远追
    不上）；外推全 A 股五年要 90GB。换 SQLite FTS5 的同机验收表：

    | 指标 | 内存倒排 | SQLite FTS5 |
    |---|---|---|
    | 启动 | 117s（重建）| **0.05s** |
    | 内存常驻 | 1.8 GB | **0.03 GB** |
    | 检索延迟 | 9 ms | 39 ms（付的代价）|
    | 增量摄取 | ~3 min | **0.8 s** |
    | retrieval@3 | 0.75 | **0.875**（BM25 的 IDF 比朴素词频更聪明）|

    **六表结构**：docs（元数据）/ chunks（正文）/ fts_w+fts_c（词
    轨+字轨两张**影子**索引，rowid 对齐 chunks.rowid）/ manifest
    （指纹账本）/ verified_facts（第 12 章记忆台账）。

    **P1 幽灵块事故（三大复盘之首）**：重摄取某文档后检索仍命中
    旧页眉块。根因：`INSERT OR REPLACE` 在主键冲突时 = DELETE+INSERT，
    chunks 换了新 rowid，而旧 rowid 的 fts 行没人清——**索引里有、
    正文里没有、检索照样命中**。修复两轮：第一轮先删后插（埋新雷：
    两个事务之间的崩溃窗口）；第二轮合并单事务（`_drop_doc_tx`
    被外层事务包住）。两个永久回归测试钉死：幽灵块测试 + 中途
    抛错原子性测试。

    **PRAGMA 连接级坑**：SQLite 的 PRAGMA 大多按连接生效——
    `_apply_pragmas` 在每次检索入口调用，注释里的警告比代码值钱。

## 4.4 动手实验

```bash
# ① schema 与索引命中解剖
bash experiments/ch04-storage-anatomy.sh
#   QUERY PLAN → SEARCH chunks USING INDEX idx_chunks_doc (doc_id=?)
#   无索引时全表扫 60.7 万行实测 31.8ms，建索引后 <0.1ms

# ② 5 行 SQL 亲手复现幽灵块（隔离库）
python - <<'EOF'
import sqlite3
con = sqlite3.connect("/tmp/ghost.db")
con.executescript("CREATE TABLE chunks(rowid INTEGER PRIMARY KEY, t);"
                  "CREATE VIRTUAL TABLE fts USING fts5(c);")
con.execute("INSERT INTO chunks(t) VALUES('营业收入')")            # rowid=1
con.execute("INSERT INTO fts(rowid, c) VALUES(1,'营业收入')")
con.execute("INSERT INTO chunks(t) VALUES('另一家公司的块')")      # rowid=2 占位
con.execute("DELETE FROM chunks WHERE rowid=1")                    # 「重灌」删旧
con.execute("INSERT INTO chunks(t) VALUES('营业收入')")            # 新 rowid=3
(rid,) = con.execute("SELECT rowid FROM fts WHERE fts MATCH '营业收入'").fetchone()
body = con.execute("SELECT t FROM chunks WHERE rowid=?", (rid,)).fetchone()
print(f"fts 命中 rowid={rid}；正文表该行 = {body}  ← 索引命中、正文缺失 = 幽灵块")
EOF
```

## 4.5 小结

- 选型三维 + 判定三问（容量算术/增量频率/进程模型）；实测表是
  决策的形态——工程选型就是选你愿意付哪笔代价；
- 原子性是「圈进同一事务」的设计决定；唯一写入口 + 影子索引 +
  对齐不变量是正文-索引一致性的三件套；
- 索引不一致的失败形态是静默的（命中已删除内容）——用永久回归
  测试钉死；
- 用执行计划验证索引命中，「建了」≠「用了」。

## 常见误区

**误区一：「生产必须上专业向量库」。**向量库解决的是大规模 ANN +
多副本 + 过滤。单机、十万级以下、词法为主的场景，SQLite/Postgres
全家桶足够且省一整条运维链。

**误区二：「SQLite 是玩具」。**它是世界上部署最广的数据库（手机/
浏览器/飞机），WAL 下读写并发成熟；边界是单写者与单机——先确认
你的场景是不是真的越界。

**误区三：「事务是数据库课的概念，用 ORM 就有了」。**事务边界是
你的设计决定：drop 与 insert 分属两个事务时，中间的崩溃窗口就是
数据消失的窗口。ORM 无关，圈法才是工程。
