# 第 4 章 存储选型：SQLite FTS5 vs 向量库 vs ES

> 状态：v0.2 · 所属：第一部 知识入库 · 前置：第 3 章

## 4.1 失败先行：1.8GB 内存与 117 秒重建

Tally v0.3 用自研**内存倒排**：60.7 万 chunk 常驻 1.8GB，每次增量
摄取后全量重建 117 秒。外推全 A 股五年（3,000 万块）需 90GB 内存——
容量墙撞上来的真实声音。

## 4.2 业界视角：RAG 存储格式全景

!!! note "背景速览"

    「向量库」只是 RAG 存储的一个子集。按查询能力分：

    | 类别 | 代表 | 查询能力 | 运维形态 |
    |---|---|---|---|
    | 嵌入式向量库 | FAISS、[Chroma](https://www.trychroma.com) | ANN 近邻 | 库/进程内 |
    | 服务型向量库 | [Milvus](https://milvus.io)、[Qdrant](https://qdrant.tech) | ANN + 过滤 + 复制 | 集群 |
    | 数据库扩展 | [pgvector](https://github.com/pgvector/pgvector) | SQL+向量 | Postgres 生态 |
    | 全文检索 | Elasticsearch、[Meilisearch](https://www.meilisearch.com)、SQLite FTS5 | BM25 词法 | 服务/嵌入 |
    | 混合引擎 | Weaviate | 词法+向量+RRF | 服务 |
    | 图数据库 | Neo4j（GraphRAG） | 关系遍历 | 服务 |
    | 结构化 | SQLite/Postgres/Mongo | SQL/文档 | 全形态 |

    三个选型维度比「哪家向量库好」更重要：①**你要什么查询**
    （词法精确 vs 语义泛化 vs 混合）？②**运维预算**（embedded 零运维
    vs server 要养）；③**容量与内存的关系**（索引能不能落盘）。
    Tally 的答案：查询以**词法精确**为主（第 5 章消融证明）、单机
    单用户、60 万块要落盘——SQLite FTS5 全中；ES 的 JVM 与集群能力
    在这个场景全是负资产。

## 4.3 决策方法：实测表，不是信仰

| 指标 | v0.3 内存倒排 | v0.4 SQLite FTS5 |
|---|---|---|
| 启动时间 | 117s（重建）/ 5s（pickle 热启） | **0.05s** |
| 内存常驻 | 1.8 GB | **0.03 GB** |
| 检索延迟（稳态） | 9 ms | 39 ms |
| 增量摄取 | ~3 min（含重建） | **0.8 s** |
| 全库 retrieval@3 | 0.75 | **0.875** |

延迟 9→39ms 是付的代价，换来容量与内存解耦、免重建增量——**工程
选型就是选你愿意付哪笔代价**。（[SQLite FTS5 文档](https://www.sqlite.org/fts5.html)）

## 4.4 六表 schema 与唯一写入口

```
docs / chunks / fts_w / fts_c / manifest / verified_facts   (+ 可选 vecs/vecmeta)
```

两条铁律（各由一次真实事故换来）：

**铁律一：Store 是唯一写入口。** 绕过 Store 直写 SQL 的路径，迟早
造出 fts rowid 与 chunks.rowid 的错位。

**铁律二：更新 = drop-then-insert，且必须同一事务。** P1 事故：
`INSERT OR REPLACE` 给 chunks 换新 rowid，旧 rowid 的 FTS 行不被覆盖
——「幽灵块」，检索命中已删除内容。演进两轮：先改先删后插；又发现
drop/insert 分属两事务，中间崩溃 = 文档消失且指纹未变永不重试——
最终单事务：

```python
# tally/store.py: add_doc（节选）
    with con:
        self._drop_doc_tx(con, doc.doc_id)     # 清旧：同事务，不自行提交
        con.execute("INSERT OR REPLACE INTO docs VALUES (?,?,?,?,?,?)", ...)
        for c in chunks:
            cur = con.execute("INSERT OR REPLACE INTO chunks VALUES (?,?,?,?,?,?,?)", ...)
            rowid = cur.lastrowid
            con.execute("INSERT INTO fts_w(rowid, content_w) VALUES (?,?)", ...)
            con.execute("INSERT INTO fts_c(rowid, content_c) VALUES (?,?)", ...)
```

对应永久回归测试：`test_readd_after_drop_no_ghost`、
`test_add_doc_failure_is_atomic`。

## 4.5 PRAGMA 是连接级的（容易踩的坑）

```python
# tally/fts.py
_PRAGMAS = ("PRAGMA cache_size=-200000", "PRAGMA mmap_size=1073741824",
            "PRAGMA temp_store=MEMORY")
# 注意 sqlite 的 PRAGMA 按连接生效——必须每次连接都设，不能做全局一次性。
```

SQLite 的 PRAGMA 大多不持久（WAL 除外）——新连接忘设，性能
silently 掉一个量级且不报错。这类静默回归只能靠代码审查与注释防御。

## 4.6 动手实验

```bash
sqlite3 tally.db ".schema chunks"        # 六表结构 + idx_chunks_doc 索引
sqlite3 tally.db "EXPLAIN QUERY PLAN
  SELECT chunk_id FROM chunks WHERE doc_id='海伦哲_2026Q1'"
# 预期：SEARCH chunks USING INDEX idx_chunks_doc
# （无索引全表扫 60.7 万行实测 31.8ms → 建索引后 <0.1ms）
```
