# 第 4 章 存储与索引：选型方法与工程不变量

> 状态：v0.5 · 所属：第二部分 语料与检索：构建证据层 · 前置：第 3 章

!!! info "本章导读"

    学完本章你能：①按「查询能力×运维预算×容量模型」三维给存储选型，
    用判定三问把内存倒排 / FTS5 / ES / 向量库分开；②讲清 Tally 六表
    schema 的分工与两条写入口铁律；③解释 FTS5 的 rowid 对齐为什么
    是生死线（幽灵块事故）；④说出 PRAGMA 连接级语义的坑；⑤用
    EXPLAIN QUERY PLAN 验证索引命中。

## 4.1 失败先行：1.8GB 内存与 117 秒重建

Tally v0.3 用自研**内存倒排**：60.7 万 chunk 常驻 1.8GB，每次增量
摄取后**全量重建索引 117 秒**。想象 `--watch` 模式（每 60 秒同步
一次）在这个架构下的样子——每次同步后 2 分钟的重建，永远追不上。

线性外推全 A 股五年（3,000 万块）需要 90GB 内存——本机差一个数量
级。这是容量墙撞上来的真实声音，也是本章所有决策的起点。

## 4.2 知识点：选型三维与判定三问

「向量库」只是 RAG 存储的一个子集。按**查询能力**分：

| 类别 | 代表 | 查询能力 | 运维形态 | 何时选 |
|---|---|---|---|---|
| 嵌入式向量库 | FAISS、[Chroma](https://www.trychroma.com) | ANN 近邻 | 库/进程内 | 原型、单进程 |
| 服务型向量库 | [Milvus](https://milvus.io)、[Qdrant](https://qdrant.tech) | ANN+过滤+复制 | 集群 | 多查询方/大数据量 |
| 数据库扩展 | [pgvector](https://github.com/pgvector/pgvector) | SQL+向量 | Postgres 生态 | 已有 PG 的团队 |
| 全文检索 | ES/OpenSearch、Meilisearch、SQLite FTS5 | BM25 词法 | 服务/嵌入 | 精确词面/数字任务 |
| 混合引擎 | Weaviate | 词法+向量+RRF 内置 | 服务 | 混合检索一步到位 |
| 图数据库 | Neo4j（GraphRAG） | 关系遍历 | 服务 | 多跳实体推理 |
| 结构化 | SQLite/Postgres/Mongo | SQL/文档 | 全形态 | 一切的底座 |

三个维度比「哪家向量库好」更重要——**查询能力 × 运维预算 ×
容量模型**。落到「内存倒排 vs FTS5 vs ES vs 向量库」这道具体题，
判定三问：

1. **容量算术**：索引必须装进内存吗？能不能落盘？（60.7 万块 ×
   向量维度 × 4 字节——先算，再谈感觉）；
2. **增量频率**：每次写入后索引要不要全量重建？（`--watch` 每
   60 秒一增量，重建 117 秒的架构直接判死）；
3. **进程模型**：单机单用户还是多查询方？要不要复制、监控、
   升级一条运维链？

Tally 的答案：查询以词法精确为主（第 5 章 D19 实测）、单机单
用户、60 万块要落盘——**SQLite FTS5 全中**；ES 的 JVM 与集群
能力在这个场景全是负资产。

## 4.3 本项目：实测表，不是信仰

换 FTS5 的同机同库验收（**决策依据的正确形态是一张实测表**）：

| 指标 | v0.3 内存倒排 | v0.4 SQLite FTS5 |
|---|---|---|
| 启动时间 | 117s（重建）/ 5s（pickle 热启） | **0.05s** |
| 内存常驻 | 1.8 GB | **0.03 GB** |
| 检索延迟（稳态） | 9 ms | 39 ms |
| 增量摄取 | ~3 min（含重建） | **0.8 s** |
| 全库 retrieval@3 | 0.75 | **0.875** |

延迟 9→39ms 是付的代价，换来容量与内存解耦、免重建增量。注意
最后一行：**检索质量不降反升**（0.75→0.875）——bm25 的 IDF 加权
比自研的朴素词频更聪明。**工程选型就是选你愿意付哪笔代价**，
前提是把每笔代价摆到桌面上。（[SQLite FTS5 文档](https://www.sqlite.org/fts5.html)）

## 4.4 本项目：六表 schema——每张表一个职责

```
docs          文档元数据（doc_id 主键：公司_期间）
chunks        块正文（chunk_id 主键；doc_id 外联；page/seq/is_table/num_notes）
fts_w / fts_c 两张 FTS5 虚拟表（词轨 unicode61 / 字轨 trigram），rowid 对齐 chunks.rowid
manifest      增量账本（path → 指纹 → doc_id）
verified_facts L1 事实台账（第 12 章）
(+ 可选 vecs / vecmeta  向量第三路，第 5 章)
```

两个容易忽略的设计：

- **fts 表是「影子」不是「副本」**：它们只存索引化文本（分词后的
  词轨 / 去空白截断的字轨），正文永远只在 chunks——一份事实，
  多个索引视图；
- **索引一致性靠 rowid 对齐**：`fts_w.rowid = chunks.rowid`——这
  是全库最脆弱的不变量，也是两条铁律存在的原因。



## 4.5 本项目：铁律一——Store 是唯一写入口

所有对六表的写操作只经 `tally/store.py` 的 Store 类。为什么这么
硬？因为绕过 Store 的直写路径迟早造出 rowid 错位——而错位的表现
是**检索命中已删除的内容**，不报任何错。事务边界与数据不变量
是设计决定，不是数据库白送的（下节的 P1 就是账单）。

## 4.6 本项目：铁律二——drop-then-insert 单事务（P1 事故全解）

**事故现场（Tally 三大复盘之首）**：重摄取某文档后，检索仍命中
旧页眉块——「幽灵块」。根因：

```sql
INSERT OR REPLACE INTO chunks ...   -- REPLACE = DELETE + INSERT
                                     -- chunks 换了新 rowid！
-- 旧 rowid 的 fts_w/fts_c 行没有被任何语句覆盖
-- → 幽灵：索引里有、正文表里没有、检索照样命中
```

修复演进两轮，值得看全过程：

**第一轮**：先删后插（`drop_doc` → insert）。正确但埋了新雷——
drop 和 insert 分属**两个事务**：drop 提交后、insert 提交前进程
崩溃 = 文档消失，而 manifest 已被 drop 清掉、指纹未变 → **永不
重试**（`--watch` 60 秒能自愈，一次性用户永远不自愈）。

**第二轮（现行）**：合并单事务：

```python
# tally/store.py: add_doc（现行版）
    with con:
        self._drop_doc_tx(con, doc.doc_id)     # 清旧：同事务，不自行提交
        con.execute("INSERT OR REPLACE INTO docs VALUES (?,?,?,?,?,?)", ...)
        for c in chunks:
            cur = con.execute("INSERT OR REPLACE INTO chunks VALUES (?,?,?,?,?,?,?)", ...)
            rowid = cur.lastrowid
            con.execute("INSERT INTO fts_w(rowid, content_w) VALUES (?,?)", ...)
            con.execute("INSERT INTO fts_c(rowid, content_c) VALUES (?,?)", ...)
```

`_drop_doc_tx` 是纯语句序列（不自带 `with con:`），被 add_doc 的
事务包住——**要么全在，要么全不在**。这正是 ACID 里 A（原子性）
的教学案例：原子性不是数据库白送的，是「你把哪些操作圈进同一个
事务」的设计决定。

两个永久回归测试钉死它：`test_readd_after_drop_no_ghost`（幽灵块）
和 `test_add_doc_failure_is_atomic`（中途抛错后旧文档完好——测试
用 `bad.page = object()` 让 sqlite3 无法适配、在 INSERT 阶段抛错，
断言旧数据原封不动）。

## 4.7 本项目：PRAGMA 是连接级的（静默性能坑）

```python
# tally/fts.py
_PRAGMAS = ("PRAGMA cache_size=-200000",     # 200MB 页缓存
            "PRAGMA mmap_size=1073741824",   # 1GB mmap
            "PRAGMA temp_store=MEMORY")
# 注意 sqlite 的 PRAGMA 按连接生效——必须每次连接都设，不能做全局一次性。
```

SQLite 的 PRAGMA 大多**不持久**（WAL 是例外，库级）——新开连接
忘了设，性能 silently 掉一个量级且不报错。Tally 的做法是
`_apply_pragmas(con)` 在每次 `search()` 入口调用。这类「静默性能
回归」没有测试可拦，只能靠**注释里的警告 + 代码审查**防御——
所以那行注释比代码本身值钱。

（WAL 与 `synchronous=NORMAL` 是 Store 打开时设的：写吞吐与崩溃
安全性的权衡，读者可自行实验两者的组合。）

## 4.8 动手实验

```bash
bash experiments/ch04-storage-anatomy.sh
# 输出实录（节选）：
#   CREATE TABLE chunks (
#     chunk_id TEXT PRIMARY KEY, doc_id TEXT, page INT, seq INT,
#     text TEXT, is_table INT, num_notes TEXT);
#   CREATE INDEX idx_chunks_doc ON chunks(doc_id);
#   == 索引命中 ==
#   QUERY PLAN
#   `--SEARCH chunks USING INDEX idx_chunks_doc (doc_id=?)

# ② 5 行 SQL 亲手复现幽灵块（隔离库，随便造）
python - <<'EOF'
import sqlite3
con = sqlite3.connect("/tmp/ghost.db")
con.executescript("CREATE TABLE chunks(rowid INTEGER PRIMARY KEY, t);"
                  "CREATE VIRTUAL TABLE fts USING fts5(c);")
con.execute("INSERT INTO chunks(t) VALUES('营业收入')")            # rowid=1（目标 doc）
con.execute("INSERT INTO fts(rowid, c) VALUES(1,'营业收入')")
con.execute("INSERT INTO chunks(t) VALUES('另一家公司的块')")      # rowid=2（别家 doc 占位）
# 幽灵三行：删旧行 → 无 rowid 重插（新 rowid=3）→ 旧 fts 行没人清
con.execute("DELETE FROM chunks WHERE rowid=1")
con.execute("INSERT INTO chunks(t) VALUES('营业收入')")
(rid,) = con.execute("SELECT rowid FROM fts WHERE fts MATCH '营业收入'").fetchone()
body = con.execute("SELECT t FROM chunks WHERE rowid=?", (rid,)).fetchone()
print(f"fts 命中 rowid={rid}；正文表该行 = {body}  ← 索引命中、正文缺失 = 幽灵块")
EOF
```

`idx_chunks_doc` 的来历值得一提：`drop_doc`/`chunks_of` 都按
doc_id 过滤——无索引时全表扫 60.7 万行实测 **31.8ms**，建索引后
**<0.1ms**（建索引 0.16s / ~15MB，一次付费永久受益）。存量库由
SCHEMA 的 `IF NOT EXISTS` 在下次 Store 打开时自动补建——**迁移
也要幂等**。

!!! example "实现练习 ★★★：影子索引维护（骨架已备）"

    `exercises/shadow-index.py`：给一个裸的 chunks 表 + fts 影子，
    实现 `add_chunk / drop_chunk`，**不变量：fts.rowid 与 chunks.rowid
    永远对齐，任何路径下不产生幽灵**。验收四断言：新增对齐、删除
    双清、同 doc 重灌（drop-then-insert）无幽灵、中途抛错回滚。
    这就是 Store 铁律的一个微缩版——做完再读 `store.py` 的
    `add_doc`，对照你的事务圈法与它的差在哪。

!!! note "前沿一瞥：图谱那一极，与 rerank 的位置"

    **GraphRAG**（[微软 2024](https://arxiv.org/abs/2404.16130)）是
    存储光谱的另一极：LLM 预建实体知识图谱 + 社区层级摘要，支持
    实体锚定的 local 查询与 map-reduce 的 global 查询——为「全语料
    综述」类问题而生。Tally 为什么不需要：财报天然带
    （公司 × 期间 × 指标）的硬结构，FTS5 + `doc_scope` 已经是
    那张「图」的键寻址版；建图的 LLM 成本与幻觉面换不来收益。
    **先问语料有没有现成结构，再决定要不要造图**。

    检索架构里还有一层位置本章没占：**rerank**（召回 → 融合 →
    重排）。`fts.py: ranking()` 的插拔式设计（向量缺位返回 None、
    静默降级双轨）已经给 reranker 留了同一个座位——它是 Tally
    roadmap 的第一项，实验设计见下一章前沿拓展。

## 4.9 小结

- 选型三维：查询能力 × 运维预算 × 容量模型；判定三问：容量算术 /
  增量频率 / 进程模型；实测表是决策的形态；
- 六表各一职责；fts 是影子索引，一致性靠 rowid 对齐；
- 两条铁律：唯一写入口；drop+insert 单事务（P1 幽灵块 + 崩溃窗口
  两轮教训）——事务边界是设计决定；
- PRAGMA 连接级：静默回归靠注释与审查防御；
- 索引幂等补建：迁移和摄取一样，要可重入。

## 常见误区

**误区一：「生产必须上专业向量库」。**向量库解决的是「大规模 ANN
+ 多副本 + 过滤」——如果你的场景是单机、十万级以下、词法为主，
SQLite/Postgres 全家桶足够，而且省掉一整条运维链。先有查询需求
（第 5 章的消融），再有存储选型；反过来就是拿着锤子找钉子。

**误区二：「SQLite 是玩具」。**SQLite 是世界上部署最广的数据库
（手机、浏览器、飞机），WAL 模式下读写并发成熟，FTS5 的 bm25
实现经过十几年锤炼。它的边界是**单写者**与**单机**——这两条
Tally 的场景全部满足（DESIGN-scale 诚实声明：>1 并发方才平移 ES）。

**误区三：「事务是数据库课的概念，用 ORM 就有了」。**事务的边界
是**你的设计决定**：drop 和 insert 分属两个事务时，中间的崩溃窗口
就是数据消失的窗口（本章 P1 的第二轮教训）。用不用 ORM 无关，
把哪些操作圈进同一个原子单元才是工程。
