## 4.1 知识：存储全景与判定三问

「向量库」只是 RAG 存储的一个子集。按查询能力看全景：

| 类别 | 代表 | 查询能力 | 运维形态 | 何时选 |
|---|---|---|---|---|
| 嵌入式向量库 | FAISS、[Chroma](https://www.trychroma.com) | ANN 近邻 | 库/进程内 | 原型、单进程 |
| 服务型向量库 | [Milvus](https://milvus.io)、[Qdrant](https://qdrant.tech) | ANN+过滤+复制 | 集群 | 多查询方/大数据量 |
| 数据库扩展 | [pgvector](https://github.com/pgvector/pgvector) | SQL+向量 | Postgres 生态 | 已有 PG 的团队 |
| 全文检索 | ES/OpenSearch、Meilisearch、SQLite FTS5 | BM25 词法 | 服务/嵌入 | 精确词面/数字任务 |
| 混合引擎 | Weaviate | 词法+向量+RRF 内置 | 服务 | 混合检索一步到位 |
| 图数据库 | Neo4j（GraphRAG）| 关系遍历 | 服务 | 多跳实体推理 |
| 结构化 | SQLite/Postgres/Mongo | SQL/文档 | 全形态 | 一切的底座 |

三个维度比「哪家向量库好」更重要——**查询能力 × 运维预算 ×
容量模型**。落到具体选型题（内存倒排 vs 全文索引 vs ES vs 向量
库），判定三问：

1. **容量算术**（先算再说）：索引必须装进内存吗？向量索引的
   账 = 块数 × 维度 × 4 字节——100 万块 × 768 维 ≈ **3GB 裸向量**
   （还没算索引结构开销与副本）；全文索引（BM25 倒排）天然落盘，
   内存只做页缓存。差一个数量级的内存模型；
2. **增量频率**：每次写入后索引要不要全量重建？HNSW 增量插入
   可行但内存常驻；BM25 倒排增量天然友好（加文档=加倒排项）；
   「每次增量后全量重建」在高频增量场景是架构性死锁；
3. **进程模型**：单机单用户还是多查询方？嵌入式（零运维）vs
   服务型（部署/监控/升级一条链）——多查询方之前，服务型的
   能力全是负资产。

**先有查询需求，再有存储选型**——第 5 章的消融会告诉你任务
到底需要什么查询能力（精确词面还是语义泛化）；反过来选就是
拿锤子找钉子。

## 4.2 知识：ANN 索引一族速成（选型必备的直觉）

如果你的检索路里有向量，绕不开近似最近邻（ANN）索引。三家主要
构造的直觉：

| 索引 | 构造直觉 | 查询/内存 | 增量 |
|---|---|---|---|
| **Flat（暴力）** | 全量精确比对 | 查询 O(N)，小库（<10万）完全够用 | 天然支持 |
| **IVF-PQ（倒排+量化）** | 聚类分桶（IVF）只查最近的几个桶；每向量压缩成几字节乘积码（PQ） | 内存省 10–30×，精度有损 | 可加桶重训 |
| **HNSW（分层小世界图）** | 多层跳表式近邻图：上层稀疏快速跳跃、底层稠密精确——像高速公路接小路 | 查询快（对数级）、召回高；**内存大**（图边常驻）| 增量插入好，删除断边麻烦 |

选型口诀：**小库暴力（Flat 又准又简单）；要省内存走 IVF-PQ
（接受召回损失）；要快又要召回走 HNSW（付内存账）**。FAISS /
Milvus / Qdrant 都同时提供三家实现——真正的问题是 4.1 的容量
算术，不是「用哪个库」。

另两个常被忽略的存储知识：

- **结构化库是底座**：元数据、权限、审计日志终究要 SQL——很多
  「向量库 vs SQL」的争论，答案是「都要，SQL 做事实源，向量库
  做加速层」；
- **GraphRAG 的位置**：图谱（[arXiv:2404.16130](
  https://arxiv.org/abs/2404.16130)）为「全语料综述/多跳实体
  推理」而生，LLM 预建实体图+社区摘要——**先问语料有没有现成
  硬结构**（财报天然有 公司×期间×指标 的键结构，图谱是重复
  建设），没有硬结构且要多跳推理才考虑。

### 演练：容量算术三档账单

判定三问第一问的实操——给三个典型库容各算一遍（bge 级 1024 维、
fp32 每维 4 字节）：

| 库容 | 裸向量内存 | +HNSW 索引开销（~1.5×）| 全文索引（BM25 倒排）| 结论 |
|---|---|---|---|---|
| 10 万块 | 1024×4×10⁵ ≈ **0.4GB** | ≈0.6GB | 落盘，页缓存几十 MB | Flat 暴力即可，向量库不必要 |
| 100 万块 | ≈ **4GB** | ≈6GB | 落盘，页缓存 ~1GB | 单机要 HNSW/IVF；或先问要不要向量 |
| 1000 万块 | ≈ **40GB** | ≈60GB | 落盘，页缓存 ~10GB | 服务化向量库/分片；先做检索消融再付这钱 |

三行账就能毙掉或立起一个选型——**先算术，后选型**。顺带两个
生态新件：[sqlite-vec](https://github.com/asg017/sqlite-vec)
（SQLite 里的向量扩展，与 FTS5 同库共存——小库混合检索的最轻
形态）；pgvector 的 HNSW 索引（已有 PG 团队的默认路）。

### 事务演练：一次重灌的全有全无

把 P1 事故的正解画成时序（v 为库内状态）：

```text
事务开始
  ├─ DELETE 旧 chunks/fts 行        （还没提交——崩溃则全部回滚，旧版完好）
  ├─ INSERT 新 chunks（rowid 41..60）
  ├─ INSERT 新 fts_w/fts_c（同 rowid 对齐）
  ├─ UPDATE docs 元数据
提交 ✓ → v2 完整落库；任一步抛错 → 回滚 → 停在 v1，账本（manifest）
  未动 → 下次摄取识别指纹差异，自动重试——失败是可重入的
```

「要么全在要么全不在」不是口号，是崩溃窗口为零的可验证性质
（案例的两个永久测试就是锚定它）。

## 4.3 知识：事务边界与数据不变量是设计决定

**ACID 的 A（原子性）不是数据库白送的**，是「你把哪些操作圈进
同一个事务」的设计决定。经典陷阱——「更新 = 先删后插」：

```text
第一轮做法：DROP 旧文档（事务1）→ INSERT 新内容（事务2）
失败形态：事务1 提交后、事务2 前进程崩溃
         → 文档消失；若外层账本（指纹）未变 → 永不重试
         （轮询型自愈掩盖不了单次用户的永久丢失）
正解：把「清旧 + 写新」圈进同一个事务，要么全在要么全不在
```

**每个存储系统都有它的「对齐不变量」**——正文与索引的一致性
约定（全文索引的 rowid 对齐、向量库的 id↔chunk 映射、图谱的
实体↔源文档）。三个通用结论：

1. **唯一写入口**：所有写操作经一个模块——事务边界、不变量
   维护、缓存失效逻辑只写一遍。绕过它的直写路径迟早造出失同步，
   而索引失同步的表象是**检索命中已删除的内容**，不报任何错；
2. **影子索引模式**：索引只存索引化文本，正文只有一份事实——
   一份数据多个索引视图；重建索引（`content=` 重建）不搬数据；
3. **静默性能回归**：很多引擎的性能参数按连接/会话生效而非持久
   （如 SQLite 的 PRAGMA 多数不跨连接）——新开连接忘了设，性能
   掉一个量级且无报错。测试拦不住，靠「集中一处、每次连接都设
   + 注释里的警告」防御。

**验证索引真的被命中**：执行计划工具（SQLite `EXPLAIN QUERY
PLAN`、PG `EXPLAIN ANALYZE`）——「建了索引」和「索引被命中」
是两件事，全表扫描 60 万行与索引命中差五个数量级，体感是 31.8ms
vs <0.1ms。

## 4.4 案例研究：Tally 的六表与幽灵块事故

!!! abstract "案例研究：Tally（store.py / fts.py）"

    **选型经过**（v0.3 → v0.4，判定三问的完整演练）：v0.3 自研
    内存倒排——60.7 万块常驻 **1.8GB**、每次增量后**全量重建
    117 秒**（`--watch` 每 60 秒一同步，永远追不上）；外推全 A
    股五年（3,000 万块）要 90GB 内存——容量算术判死。换 SQLite
    FTS5 的同机验收：

    | 指标 | 内存倒排 | SQLite FTS5 | 读法 |
    |---|---|---|---|
    | 启动 | 117s（重建）| **0.05s** | 落盘免重建 |
    | 内存常驻 | 1.8 GB | **0.03 GB** | 60 倍 |
    | 检索延迟 | 9 ms | 39 ms | **付的代价**（页缓存换内存）|
    | 增量摄取 | ~3 min | **0.8 s** | 增量友好 |
    | retrieval@3 | 0.75 | **0.875** | BM25 的 IDF 比朴素词频聪明 |

    **工程选型就是选你愿意付哪笔代价**——前提是把每笔摆上桌面。

    **六表 schema**（每张一个职责）：

    ```text
    docs           文档元数据（doc_id 主键 = 公司_期间）
    chunks         块正文（page/seq/is_table/num_notes）
    fts_w / fts_c  词轨+字轨两张 FTS5 影子表，rowid 对齐 chunks.rowid
    manifest       增量账本（path → 指纹 → doc_id）
    verified_facts L1 记忆台账（第 12 章）
    ```

    **P1 幽灵块事故**（三大复盘之首）——表象：重摄取某文档后，
    检索仍命中旧页眉块。根因：`INSERT OR REPLACE` 在主键冲突时 =
    DELETE+INSERT，**chunks 换了新 rowid，旧 rowid 的 fts 行没人
    清**——索引里有、正文里没有、检索照样命中。修复两轮：

    ```python
    # tally/store.py: add_doc（现行版——第二轮修复）
    with con:                                        # 单事务圈住清旧+写新
        self._drop_doc_tx(con, doc.doc_id)           # 纯语句序列，
        con.execute("INSERT OR REPLACE INTO docs …")  # 不自带 with——
        for c in chunks:                              # 被外层事务包住
            cur = con.execute("INSERT OR REPLACE INTO chunks …")
            rowid = cur.lastrowid
            con.execute("INSERT INTO fts_w(rowid, content_w) VALUES (?,?)", …)
            con.execute("INSERT INTO fts_c(rowid, content_c) VALUES (?,?)", …)
    ```

    第一轮（先删后插）埋了新雷：两个事务之间的崩溃窗口；第二轮
    合并单事务才收口。两个**永久回归测试**钉死：
    `test_readd_after_drop_no_ghost`（幽灵块）与
    `test_add_doc_failure_is_atomic`（中途抛错旧文档完好——测试
    用 `bad.page = object()` 让 sqlite3 适配失败在 INSERT 阶段）。

    **PRAGMA 连接级坑**：`_PRAGMAS`（200MB 页缓存/1GB mmap/内存
    临时表）在**每次** `search()` 入口重设——注释「PRAGMA 按连接
    生效」比代码本身值钱。**索引实测**：`idx_chunks_doc` 建前
    31.8ms、建后 <0.1ms（60.7 万行），存量库由 SCHEMA 的
    `IF NOT EXISTS` 自动补建——**迁移也要幂等**。

## 4.5 动手实验

```bash
# ① schema 与索引命中
bash experiments/ch04-storage-anatomy.sh
#   QUERY PLAN → SEARCH chunks USING INDEX idx_chunks_doc (doc_id=?)

# ② 5 行 SQL 亲手复现幽灵块（含 SQLite 的 rowid 重用坑）
python - <<'EOF'
import sqlite3
con = sqlite3.connect("/tmp/ghost.db")
con.executescript("CREATE TABLE chunks(rowid INTEGER PRIMARY KEY, t);"
                  "CREATE VIRTUAL TABLE fts USING fts5(c);")
con.execute("INSERT INTO chunks(t) VALUES('营业收入')")            # rowid=1
con.execute("INSERT INTO fts(rowid, c) VALUES(1,'营业收入')")
con.execute("INSERT INTO chunks(t) VALUES('另一家的块')")          # rowid=2 占位
con.execute("DELETE FROM chunks WHERE rowid=1")                    # 注意：空表会让
con.execute("INSERT INTO chunks(t) VALUES('营业收入')")            # SQLite 重用
(rid,) = con.execute("SELECT rowid FROM fts WHERE fts MATCH '营业收入'").fetchone()
print("fts 命中 rowid=%d；正文 = %s ← 幽灵" %
      (rid, con.execute("SELECT t FROM chunks WHERE rowid=?", (rid,)).fetchone()))
EOF
```

## 4.6 小结

- 选型三维 + 判定三问；容量算术先算（向量 3GB vs 倒排落盘）、
  增量频率（重建 vs 增插）、进程模型（负资产判断）；
- ANN 一族直觉：小库暴力/省内存 IVF-PQ/快而贵 HNSW——SQL 做事实
  源、加速层做视图；图谱先问语料有无现成硬结构；
- 原子性是「圈进同一事务」的设计决定；唯一写入口 + 影子索引 +
  对齐不变量是正文-索引一致性三件套；失同步是静默失败，用永久
  回归测试钉死；
- 静默性能回归（连接级参数）靠集中设置+注释防御；执行计划验证
  「建了」≠「用了」。

## 常见误区

**误区一：「生产必须上专业向量库」。**向量库解决大规模 ANN +
多副本 + 过滤；单机十万级以下词法为主，SQLite/Postgres 全家桶
足够且省一整条运维链。

**误区二：「SQLite 是玩具」。**部署最广的数据库（手机/浏览器/
飞机），WAL 下读写并发成熟；边界是单写者与单机——先确认真的
越界再迁移。

**误区三：「事务用了 ORM 就有了」。**事务边界是你的圈法：drop
与 insert 分属两事务时，中间的崩溃窗口就是数据消失的窗口。

**误区四：「索引建了就快了」。**执行计划说了算——索引不被命中
（类型不匹配、函数包裹列、优化器误判）时照样全表扫描。
