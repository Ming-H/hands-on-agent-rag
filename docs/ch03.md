## 3.1 知识：切分的第一问——语义单元是什么

切分（chunking）是 RAG 里被讨论最多的低层决策。选型第一问不是
「chunk 多大」，是**这个语料的语义单元是什么**——财报是「表格
行」（标签+数值+同比），判决书是「条」，药品说明书是「节+表」，
新闻是「段落」。切分器的职责是**沿语义单元的边界切**，而不是沿
字符数切。

业界谱系六代：

| 方法 | 代表实现 | 思路 | 软肋 |
|---|---|---|---|
| 固定长度 | 朴素 token 切分 | 简单、可并行 | 拦腰斩断语义单元 |
| 递归分隔 | [LangChain RecursiveCharacterTextSplitter](https://python.langchain.com/docs/how_to/recursive_text_splitter/) | 段落→句子→字符逐级回退 | 仍不识表格结构 |
| 句子/语义窗口 | [LlamaIndex SentenceSplitter](https://docs.llamaindex.ai)、语义分块（Kamradt）| 按句/按嵌入相似度断点 | 表格行≠句子；嵌入断点贵且不稳定 |
| 版面感知 | [Unstructured chunk_by_title](https://unstructured.io) | 按标题/布局聚块 | 依赖上游版面分析 |
| 命题级 | Dense X Retrieval（命题=原子事实句）| 一句一命题 | 块数爆炸、丢上下文 |
| 迟到切分 | Late Chunking（[arXiv:2409.04701](https://arxiv.org/abs/2409.04701)）| 整文嵌入后按块池化 | 需长上下文嵌入模型 |

经验参数（主流实践 256–1024 token、overlap 10–20%）全部来自
**叙事文本**的直觉——overlap 本身就是「切错了再补救」的设计。
**chunk 大小没有魔法数字**；把叙事直觉套在表格文档上，是切分层
最常见的错。

## 3.2 知识：small-to-big 与上下文增强——切分问题的另一半

**small-to-big**：检索单元用小的（精确命中），生成上下文用大的
（读懂结构），两者解耦。LlamaIndex 的 sentence-window 是这个模式
的句级实现：检索命中一句，送进生成的是 ±窗口的邻居。它回答了
「小块保检索精度」与「大块保上下文完整」的矛盾——**不必二选一**。

**上下文增强**（Contextual Retrieval，[Anthropic 2024](
https://www.anthropic.com/research/contextual-retrieval)）：块
脱离上下文就检索不准——索引前给每块 prepend 一段 LLM 生成的
上下文，实测 top-20 检索失败率 **5.7% → 3.7%**（上下文嵌入）
→ **2.9%**（+上下文 BM25）→ **1.9%**（+rerank）。代价是每块一次
LLM 调用、生成的上下文本身有幻觉面。与 Late Chunking 同族思想：
**让块带着上下文被检索**。

**表格保全**：数字密集型语料的命门。固定边界切一行表格数据的三
种死法——指标与数值分家（两个半块谁也组装不出事实）、同行多值
分离（本期/上期/同比成孤儿）、切在千分位逗号后（碎片不可读）。
对策是**结构感知聚簇**：识别表格行 → 连续表格行聚成原子块 →
**永不跨切**；纯列头行（无数字）过滤掉——它们词面完美（含实体
名+期间词）却是检索噪声。切分器越是「不识结构」，越需要 overlap
这种补丁；识别了结构，overlap 就不需要了。

## 3.3 案例研究：Tally 的表格感知分块

!!! note "案例研究：Tally（ingest.py）"

    **行分类器 6 行启发式**：数字密集（数字占比 ≥25% 或 ≥2 个
    千分位数字）、无句末标点、行长 ≤120——三条判表格行；连续
    表格行聚簇永不跨切；`keep_block` 过滤纯列头块（列头凭「公司名
    +期间」的完美词面会挤掉真值块，实测）。

    **形态实测**：全库 **42.1% 的块是完整表格块**。毁伤实验
    （把分类器改成恒 False 重建库跑评测）：叙述型语料（业绩预告）
    **不疼**——answer_hit 1.0 不变，只是块数 310→76；表格重语料
    （年报/季报）**当场崩**——innolight 31 题 1.0 → **0.778**。
    结论：**毁伤面取决于语料形态——先做形态统计，再选切分器**。

    **num_notes 换算注释**：摄取时给每块附程序换算的量纲注释
    （`41,914.72 万元 → ≈4.19亿`；只匹配带千分位大数防年份误换，
    每块 ≤6 条）。它是 Contextual Retrieval 的**确定性轻量变体**：
    零 LLM 成本、零幻觉面，只补「量纲鸿沟」这一种最痛的缺——
    用户问「多少亿」而原文写「万元」时，词面零重叠。**换算在
    摄取层做一次**，检索/打分/生成每层直接用，不在在线路径重算。

    **已知边界（挂账未修）**：超长表格（>840 字）切块后列头只在
    首块——Tally 把它写进边界账本（DESIGN-v0.6 §9），修法的副作用
    （表头复制引入重复块污染检索）大于收益，权衡后挂账。

!!! example "迁移盒：法律文书 / 药品说明书怎么切"

    - **语料差异**：判决书的语义单元是「条目」（诉讼请求/事实
      认定/裁判理由各成块）；说明书是「节+表」，用法用量是生死
      攸关的表格行。
    - **哪个决策因此改变**：行分类器要换——判决书按「第 X 条」
      边界聚簇；说明书保留表格感知但**永不跨节**（「用法用量」
      的行绝不与「不良反应」粘连）；num_notes 扩族（mg/μg/IU 与
      按体重折算）。
    - **Tally 哪个机制对应**：聚簇永不跨切的骨架原样，换的是
      行分类器——这正是 3.1 第一问的实操。产物记进画布第 3 格。

## 3.5 小结

- 切分第一问：语料的语义单元是什么——chunk 大小没有魔法数字；
- 六法谱系共同的坑是把叙事直觉（overlap、固定窗口）套在结构化
  文档上；
- small-to-big 解开「检索精度 vs 上下文完整」的矛盾；上下文增强
  用生成补语境（有幻觉面），结构感知用规则保结构（零幻觉面）；
- 毁伤面取决于语料形态：叙述型不疼、表格型崩——先统计再选器。

## 常见误区

**误区一：「chunk 越小检索越准」。**小块提升检索信噪比，但摧毁
上下文：孤立的数字块没有标签就不可读。切分是在检索精度与上下文
完整性之间找平衡，方向由语义单元决定。

**误区二：「overlap 是万能解药」。**overlap 的本质是**复制内容**
——同一句出现在两个块里，检索时互相竞争、引用时重复计数。它是
「切错了再补救」的设计；按语义单元切的方案不需要它。

**误区三：「语义切分（嵌入断点）总是更好」。**①成本高一个量级；
②对表格无效（表格行的「语义相似度」测不出列结构）；③断点不稳定
——同一文档两次切分可能不同，破坏增量幂等。
