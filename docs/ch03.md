## 3.1 知识：切分第一问与六法谱系

切分（chunking）要同时伺候两个主人：**检索**（要小块——信噪比
高、命中精确）和**生成**（要大块——上下文完整、结构可读）。
所有切分方法都在这对矛盾里选位置。

选型第一问不是「chunk 多大」，是**这个语料的语义单元是什么**：
财报是「表格行」（标签+数值+同比），判决书是「条」，药品说明书
是「节+表」，新闻是「段落」，代码是「函数」。切分器的职责是
**沿语义单元边界切**——这句话判死刑了「固定 512 token」的默认
直觉。

六法谱系（每法的软肋比优点更重要）：

| 方法 | 代表 | 思路 | 软肋 |
|---|---|---|---|
| 固定长度 | 朴素 token 切分 | 简单、可并行 | 拦腰斩断语义单元 |
| 递归分隔 | [RecursiveCharacterTextSplitter](https://python.langchain.com/docs/how_to/recursive_text_splitter/) | 分隔符优先级逐级回退（段落→句→字符）| 仍不识表格结构 |
| 句子/语义窗口 | [SentenceSplitter](https://docs.llamaindex.ai)、语义分块（Kamradt）| 按句切或按嵌入相似度断点 | 表格行≠句子；嵌入断点贵且**不稳定**（同文档两次切分可能不同——破坏增量幂等）|
| 版面感知 | [Unstructured chunk_by_title](https://unstructured.io) | 按标题/布局聚块 | 依赖上游版面分析质量 |
| 命题级 | Dense X Retrieval（[arXiv:2312.06648](https://arxiv.org/abs/2312.06648)）| 一句一原子命题 | 块数爆炸、上下文全失 |
| 迟到切分 | Late Chunking（[arXiv:2409.04701](https://arxiv.org/abs/2409.04701)）| 整文过 embedding 模型后按块池化 token 级向量——块向量自带全文语境 | 需长上下文嵌入模型；索引构建流程变 |

经验参数（256–1024 token、overlap 10–20%）全部来自**叙事文本**
的直觉。overlap 值得单独说透：它的本质是**复制内容来缓解斩断**——
同一句出现在两个块里，检索时互相竞争、引用时重复计数。它是
「切错了再补救」的设计；**沿语义单元切得准，就不需要 overlap**。
「chunk 大小没有魔法数字」——先做形态统计（表格块占比、平均段
长），再定参数。

## 3.2 知识：small-to-big 与上下文增强——矛盾的解法

「小块保检索、大块保生成」的矛盾有三个层次的解法：

**① small-to-big（检索单元与生成单元解耦）**：索引用小块（精确
命中），命中后把 ±邻居窗口一起送生成（结构完整）。LlamaIndex 的
sentence-window 是句级实现（检索单句、送 ±window）；页级实现是
「命中页 ±N 块」。这是**免费的**解法——只改组装逻辑，不动索引。

**② 父子块（parent-child retriever）**：索引子块，命中后上溯
送父块（章节/页）。适合层级强的语料（手册、法典）。

**③ 上下文增强（Contextual Retrieval，[Anthropic 2024](
https://www.anthropic.com/research/contextual-retrieval)）**：
块脱离上下文就检索不准（「该公司 2024 年营收增长 30%」——
「该公司」是谁？）。索引前给每块 prepend 一段 LLM 生成的上下文
说明，实测 top-20 检索失败率逐级下降：

```text
基线嵌入           5.7%
+上下文嵌入        3.7%   （生成式上下文拼进块再嵌入）
+上下文 BM25       2.9%   （混合检索加一路词法）
+rerank           1.9%   （精排收尾，第 5 章）
```

代价：每块一次 LLM 调用 + 生成上下文自身的幻觉面。适合高价值、
低频更新的语料；对增量高频语料，**确定性变体**更稳——程序可
计算的上下文（量纲换算、所属章节名、实体标注）零成本零幻觉，
只覆盖「可计算的那类缺」。

**表格保全**——数字密集语料的命门。固定边界切表格行的三种死法：

```text
营业收入 520,053,589.94  345,593,109.95  50.48%
① 指标与数值分家：检索「营业收入」命中无数字块，检索数字命中
   无标签块——两个半块谁也组装不出事实
② 同行多值分离：本期/上期/同比进两块——「营收 5.2 亿」和
   「增长 50.48%」从此是孤儿
③ 切在千分位逗号后：520, 与 053,589.94——两个块各自不可读
```

对策 = **结构感知聚簇**：行分类器识别表格行 → 连续表格行聚成
原子块 → **永不跨切**；纯列头行过滤（「项目 2026年半年度
2025年半年度」这种无数字行，词面完美——含实体名+期间词——检索
必命中，信息量为零，还会挤掉真值块）。分类器可以是规则（数字
密度+无句末标点+短行，第 3.3 案例的 6 行启发式）也可以是模型
（Docling 的表格检测），**规则优先**——切分是离线高频路径，
第 1 章信任分级说该给确定性代码。

## 3.3 案例研究：Tally 的表格感知分块

!!! abstract "案例研究：Tally（ingest.py）"

    **行分类器——6 行启发式，零模型零成本**：

    ```python
    # tally/ingest.py: _is_table_line（判定骨架）
    def _is_table_line(line: str) -> bool:
        s = line.strip()
        if not s or len(s) > 120:            # 太长不是表格行（PDF 行粘连）
            return False
        if _SENT_END.search(s):              # 有句末标点 → 叙述句
            return False
        digits = len(_TABLE_HINT.findall(s))
        return digits >= max(2, len(s) * 0.25) or ("  " in s and digits >= 2)
    ```

    三条判据的物理含义：数字密集（密度 ≥25% 或 ≥2 个千分位数字）
    /无句末标点（表格行不是完整句子）/短行（叙述才粘连成长行）。
    配套三件：**连续表格行聚簇永不跨切**（`chunk_page` 的聚簇
    循环，chunk_id 连号可验证）；**`keep_block` 过滤纯列头块**
    （实测：列头凭「公司名+期间」的完美词面把真值块挤出 top-8）；
    **正文按段落边界切 ~420 字**（实测平衡点；DESIGN-v0.6 §5 的
    切分审计：真实 420 字溢出切割占正文块 30%——数字是权衡不是
    拍脑袋）。

    **形态实测与毁伤实验**（全书最疼的一组数字，2026-10-22）：
    全库 **42.1% 的块是完整表格块**。把 `_is_table_line` 改成
    恒 False 重建库跑评测：

    | 语料 | 块数 | answer_hit |
    |---|---|---|
    | samples（叙述型预告）| 310 → 76 | 1.0 → **1.0**（不疼——事实住在句子里）|
    | innolight（表格重年报）| 7,873 → 4,075 | 1.0 → **0.778**（31 题掉 7 题，CI 门槛当场红）|

    **毁伤面取决于语料形态**——这个结论比「切分很重要」诚实得多
    也更有用：先统计形态，再决定在切分上花多少力气。

    **num_notes 数字注释**（Contextual Retrieval 的确定性轻量
    变体）——摄取时给每块附程序换算的量纲注释：

    ```python
    # tally/ingest.py: normalize_numbers（骨架）
    _NUM_RE = re.compile(r"([1-9]\d{0,2}(?:,\d{3})+(?:\.\d+)?)\s*(亿元|万元|元)")
    # 41,914.72 万元   → ≈4.19亿      只匹配带千分位大数——
    # 644,051,473.82 元 → ≈6.44亿      「2026 年」这类年份不换算
    # 1,234.56 亿元    → ≈1,234.56亿   亿元原样
    ```

    三条纪律：只匹配千分位大数（防年份误换）；每块至多 6 条（防
    大表刷屏）；**换算在摄取层做一次**——此后检索、打分、生成每
    层直接用，不在任何在线路径重算。它解决的是「用户问多少亿、
    原文写万元」的量纲鸿沟（词面零重叠）——用户问「欧科亿预计
    净利润多少亿元」时，正是这条注释接上了检索。

    **已知边界（挂账未修）**：超长表格（>840 字）切后列头只在
    首块——后块是无列名的裸数字行。修法的副作用（表头复制进每
    块 → 重复块污染检索）大于收益，权衡后写进边界账本（DESIGN-
    v0.6 §9）。「知道哪里没修好、为什么暂不修」是工程教程最值钱
    的部分之一。

### 演练：一页财报走完切分全流程

拿一页典型「主要会计数据」表（第 3 页），看固定切分 vs 结构感知的
逐行差异（构造示例，数字取自样例语料形态）：

```text
原文（抽取后，行序即 PDF 指令流序）：
  项目                    2026年1-3月    2025年1-3月    增减(%)
  营业收入               520,053,589.94 345,593,109.95   50.48
  归属于上市公司股东的净利润 61,282,301.80 45,104,755.32   35.90
  ……（共 14 个指标行）
  报告期内，公司经营情况稳定，主要系下游需求回暖所致。
```

**固定 512 字符切**：切点大概率落在「52」与「0,053,589.94」之间
——检索「营业收入」命中无数字的前半块、检索「50.48」命中无标签的
后半块；同比列与本期列可能分家。三种死法一页全中。

**结构感知聚簇**：列头行（`keep_block` 过滤——无数字纯噪声）→
14 个指标行聚成一个原子块（永不跨切）→ 末句叙述句独立成块。
检索「营业收入 同比」→ 单块同时含标签、本期值、同比值——**一个
块就是一条完整事实**。

块数对照（案例实测的库里）：这一页固定切法约 5–7 块（半数残缺），
聚簇后 2 块（表块 + 叙述块），块数更少、每块更完整——切分不是
切得越碎越好，是**沿语义边界切**。

!!! example "迁移盒：法律文书 / 药品说明书怎么切"

    - **语料差异**：判决书语义单元是「条」（条号是天然锚，表格
      启发式帮不上）；说明书是「节+表」，用法用量是生死攸关的
      表格行。
    - **哪个决策因此改变**：行分类器换判据——判决书按「第 X 条」
      边界聚簇；说明书保留表格感知但**永不跨节**（「用法用量」
      的行绝不与「不良反应」粘连）；num_notes 扩族（mg/μg/IU 与
      按体重折算）。
    - **Tally 哪个机制对应**：聚簇永不跨切的骨架原样，换的是行
      分类器——3.1 第一问的实操。记进画布第 3 格。

!!! tip "设计清单（切分层）"

    - [ ] 语义单元第一问的答案写下来了吗（表格行/条/节/段）
    - [ ] 形态统计跑了几个数：表格块占比、平均段长、扫描件占比
    - [ ] 行分类器三条判据（数字密度/无句末标点/短行）适配你的语料吗
    - [ ] 列头过滤开了吗——你的语料有「词面完美无信息」的行吗
    - [ ] 需要上下文增强吗：生成式（贵/全）vs 确定性（免费/窄）
    - [ ] overlap 为什么不需要——能一句话讲给你的同事吗


## 3.5 小结

- 切分第一问：语料的语义单元是什么；chunk 大小没有魔法数字，
  经验参数全是叙事文本的直觉；
- 六法谱系软肋各异；语义切分不稳定会破坏增量幂等；overlap 是
  「切错了再补救」，沿语义单元切就不需要它；
- 「检索精度 vs 上下文完整」三层解法：small-to-big（免费）/
  父子块（层级语料）/上下文增强（生成式 5.7→1.9%，确定性变体
  零幻觉）；
- 表格保全 = 行分类 + 聚簇永不跨切 + 列头过滤；毁伤面取决于
  形态（叙述不疼、表格崩 22 个点）——先统计再选器。

## 常见误区

**误区一：「chunk 越小检索越准」。**信噪比高是真的，但孤立数字
块没有标签不可读——抽取式选不出、LLM 读不懂。切分是找平衡，
方向由语义单元决定。

**误区二：「overlap 是万能解药」。**overlap 复制内容：检索竞争、
引用重复计数。识别结构后 overlap 是负资产。

**误区三：「上了 Docling/MinerU 就不用管切分了」。**解析器输出
的 element 只是把「表格识别」做完，聚簇策略（永不跨切、列头
过滤）仍是你的设计决定。

**误区四：「切分参数调到最优就完事」。**语料会长、版式会变——
切分审计（溢出切割占比、表格块占比）应该随 CI 跑，形态漂移
时重新校准。
