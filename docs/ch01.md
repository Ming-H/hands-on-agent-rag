# 第 1 章 开篇：为什么你的 RAG Demo 上不了线

> 状态：v0.3 · 所属：第一部 知识入库 · 先修：会 Python、调过 LLM API

!!! info "本章导读"

    学完本章你能：①说出 Demo 与生产 RAG 的三个本质差距（不知道自己
    不知道/口径混淆/不可靠环节交给不可靠组件）；②用自己的话讲清
    「对账」与封闭世界契约；③跑通 Tally 并读懂它的架构总图；④判断
    一个 RAG 系统处在业界谱系的哪一代。

## 1.1 失败先行：三个让 Demo 现场的提问

先跑起来，再让它在三个问题上当场翻车——**先看失败再学设计**，是
全书的方法论，也是 Tally 这个项目真实的成长方式。

```bash
git clone https://github.com/Ming-H/tally.git && cd tally
pip install -r requirements.txt
python -m tally.cli ingest samples/    # 30 秒：摄取 3 家公司 5 份样例财报
```

**提问一：问一个库里没有的年份。**

```bash
python -m tally.cli ask "欧科亿 2030 年净利润预测"
```

Tally 的回答（实测输出）：

> 库里没有 2030 年期间的报告（现有期间：2024FY、2024H1、2024Q1、
> 2024Q3、2025FY、2025H1、2025Q1、2025Q3、2026H1、2026H1E、
> 2026Q1）。对不上账，不硬答。

注意这个拒答的三个细节：**指名缺什么**（2030 年）、**列出现有什么**
（11 个期间全列出）、**拒绝的代价为零**（用户立刻知道该问什么）。
对比一个「普通」RAG Demo 的做法：检索出 2026 年的数字，配上
「根据现有资料，欧科亿净利润为…」的措辞——流畅、自信、答非所问。
用户没发现就埋了雷，发现了就再也不信这个系统。

**Demo 缺的第一样东西：知道自己不知道什么。**

**提问二：问扣非净利润。**

```bash
python -m tally.cli ask "中际旭创 2025 年一季度扣除非经常性损益后的净利润多少"
```

正确答案只有一个：**1,568,385,287.19 元**（扣非口径）。但库里同页
躺着它的孪生兄弟——归母净利润 **1,582,876,128.67 元**。两个数字
相差 1%，词面重叠 80%，向量相似度极高——语义检索**天生喜欢**这种
「近而不同」。典型 Demo 会毫不犹豫地抓起归母的数（它排在更前面），
挂上真页码引用，verify 通过——错得无懈可击。

**Demo 缺的第二样东西：口径（caliber）意识。**这是财报域的灵魂
概念，第 9 章用整章讲 Tally 为它修的五层防线。

**提问三：问趋势。**「最近几个季度利润走势如何？」——让 LLM 自己
逐期检索，小模型的实测行为：漏掉一两个季度、把同一个季度查两遍、
把「预计」答成「已实现」。Tally 的解法是把期间遍历收走，做成
确定性代码（`trend_research`），模型只负责最后的叙述。

**Demo 缺的第三样东西：把不可靠的环节交给可靠的代码。**

## 1.2 业界视角：RAG 的谱系与本书的位置

!!! note "背景速览"

    RAG（Retrieval-Augmented Generation）由 Lewis et al. 2020 年提出
    （[arXiv:2005.11401](https://arxiv.org/abs/2005.11401)）：生成前
    先检索，用外部知识约束模型输出。此后业界走出一条谱系（Gao
    et al. 综述 [arXiv:2312.10997](https://arxiv.org/abs/2312.10997)）：

    | 代际 | 形态 | 典型特征 | 代表问题 |
    |---|---|---|---|
    | Naive RAG | 检索→拼接→生成 | 一把向量库一把 prompt | 「检索到的就答，没检索到也答」|
    | Advanced RAG | 查询改写、重排、混合检索 | 上下文工程 | 「检索更好了，但出口没人管」|
    | Modular/Agentic | 路由、纠错环、工具、规划 | LLM 决定控制流 | 「链更长，失败怎么传播？」|
    | **可信 RAG（本书）** | 出口闸门、归因、拒答 | **答案凭什么出门** | —— |

    一个直观的对照：前三代都在回答「怎么查得更好」，第四代回答
    「答案能不能出门」。这不是谁的错——教程生态自然集中于前三代
    （它们有现成框架和明确的指标），而第四代需要你拥有一个敢被
    评测出错的系统。这就是本书用真实项目当载体的原因。

    Anthropic 在 [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)
    里的建议与此同构：从能工作的最简单结构开始（workflow），只在
    评估证明需要时再加自主性（agent）。Tally 的立场一句话：
    **自由规划、强制对账**——控制流可以给模型，出口必须留给代码。

## 1.3 对账思想：Tally 这个名字

中世纪的符木（tally stick）：债权双方把数目刻在一根木棍上，从中间
劈开，各执一半。对账时把两半合上——**刻痕对得上，账才算数**。

```
   你的那一半（答案）              原文的那一半（证据）
   ┌┐┬┐┬┐┬┐┬┐                  ┌┐┬┐┬┐┬┐┬┐
   └┘┴┘┴┘┴┘┴┘   ←—— 对上才放行 ——→  └┘┴┘┴┘┴┘┴┘
   「净利 41,922.46 万元」          块原文里真的有这句
                                  [欧科亿_2026H1E 第1页]
```

这个思想在学术界有个正式名字：**归因（Attribution）**。Rashkin
et al. 的 AIS 框架（[arXiv:2112.12870](https://arxiv.org/abs/2112.12870)，
[ACL 版](https://aclanthology.org/2023.cl-4.2)）把标准定为「一个
知情读者会同意：根据来源 s，陈述 z 成立」，并给出可操作的判定
等级（E 完全可归因 / C 可补全 / N 不可归因）。Tally 的 verify
闸门是 AIS 的工程化：**每句答案必须能在证据池里对上刻痕**；对不上，
降级成纯引用原文的抽取式回答；连原文都没有，拒答。

为什么这件事值得单独写一本书？因为「模型不编」和「系统保证模型
不编」是两回事：前者靠祈祷（换个模型就变天），后者靠结构（什么
模型来都一样）。本书讲的是后者。

## 1.4 封闭世界契约：三条军规

Tally 的 v0.7 契约只有三条，却是全系统成立的前提：

1. **事实只来自内部 RAG 证据**——LLM 的参数知识可以组织语言，
   永远不产出事实。它可以说「以上数据显示…」，不可以说「据我所知…」。
2. **工具白名单只有内部动作**（search / metrics_table / derive）——
   永无浏览器、外部 API、模型生成的代码。模型无权自造工具。
3. **只有 verify:pass 的结构化事实进长期记忆**——记忆是加速器，
   不是后门（第 11 章展开：写闸、读不豁免、指纹失效）。

**为什么必须封闭世界？**开放世界里 verify 永远证伪不了「模型碰巧
知道」：答案对了，你无法区分它是检索到的（可信）还是编得恰好对了
（不可信）——而两者的可靠性模型完全不同。封闭世界把「对账」变成
可判定问题：答案句 → 证据池 → 找得到/找不到，二值。

这也是 Tally 与 CRAG 这类「检索不够就上网补」的路线
（[arXiv:2401.15884](https://arxiv.org/abs/2401.15884)）的根本分野：
金融场景里，一个语义相近的网页比一句「找不到依据」危险得多。
**宁缺毋滥是领域知识，不是技术缺陷。**

## 1.5 双脑架构：一张图看全书

```
离线：PDF/MD ─→ 文件名元数据 ─→ 页眉剥离 ─→ 表格感知分块 ─→ 数字归一化
                （SHA-256 指纹增量：增/改/删自适应）          ← 第 2、3 章
                     ↓
              SQLite（六表 + FTS5 双轨倒排）                   ← 第 4 章

在线（LangGraph 状态机）：
  问题 → understand（LLM 理解 + 八守卫）                     ← 第 6 章
        → memory_probe → route（期间守卫）
        ├── 多跳信号 → plan（只删不造）→ agent_research（ReAct）← 第 10、11 章
        ├── heuristic → retrieve（双轨 FTS + RRF）→ grade ⇄ rewrite ← 第 5 章
        ├── trend → trend_research（确定性遍历 + 单季差分）
        └── other → refuse
        → generate（grounded，逐句带 [公司_报告期 第N页] 引用）  ← 第 7 章
        → verify_citations（覆盖率 <0.45 降级 / 无据拒答）       ← 第 8、9 章
                                                              ← 评测与边界：第 12、13 章
```

读这张图的三个要点：

- **所有路径汇入同一个出口**（verify_citations）——Agent 自主检索、
  记忆命中、差分派生，谁也别想绕过闸门（第 8 章）；
- **同一张图、两个大脑**：LLM 模式与零 key 的规则模式（heuristic）
  跑同一套节点与闸门。heuristic 是可复现的回归基线——本书几乎每个
  实验都用它当确定性对照组（这也是为什么全书的实验数字人人可复现）；
- **离线层决定在线层的天花板**：第 2 章的确定性元数据，在第 6 章
  兑现成确定性期间守卫——层的红利会延迟兑现，但一定兑现。

## 1.6 动手：跑通 + 第一次被拒答

```bash
python -m tally.cli ask "欧科亿 2026 年半年度预计净利润多少"
# → 预计净利润 36,000 万元至 42,000 万元（约 3.60 亿元至 4.20 亿元）
#   [欧科亿_2026H1E 第1页]

python -m tally.cli ask "欧科亿 2030 年净利润预测"
# → 库里没有 2030 年期间的报告……对不上账，不硬答。

python -m tally.cli eval    # 七数据集 84 题评测，一条命令复现全部指标
```

第三个命令值得专门看一眼输出——七行指标（retrieval@3 / answer_hit /
refusal / citation_coverage / chunk P/R@8 / steps）是全书的「体温计」，
第 12 章逐个拆解它们的口径与陷阱。

!!! tip "诊断态三档"

    Tally 的观测性是分层的，后面章节会反复用到：
    `ask "…"` 产品态（干净答案）；`ask "…" -v` 诊断态（stderr 打印
    trace 每节点耗时，如 `understand:rule(0ms) → route:compare(36ms)
    → decompose:… → verify:pass(0.962)`）；`ask "…" --json` 机器态
    （整态 JSON，修前修后对比可脚本化）。**读 trace 是本书实验课的
    基本功。**

## 1.7 小结

- Demo 与生产的三个差距：不知无知、口径混淆、不可靠环节放错位置；
- 对账 = AIS 归因的工程化：答案句 ↔ 证据池刻痕对得上才出门；
- 封闭世界契约三条：事实只出自证据 / 工具白名单 / 过闸才进记忆；
- 双脑同图同闸：heuristic 是基线，LLM 是大脑，出口只有一个。
